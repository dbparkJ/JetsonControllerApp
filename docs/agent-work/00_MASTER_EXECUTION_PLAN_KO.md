## 1. 확정된 제품 방향

- 1차 제품 목표는 **사내 현장 운영용**이다.
- 2026년 11월 첫째 주 엑스포가 있고, **시연 준비 마감은 2026년 10월 중순**이다.
- 현장 정식 투입 일정은 미정이다.
- 엑스포에서는 실장치 전체 구동보다 **앱과 준비된 자료를 중심으로 보여주는 시연**을 우선한다.
- 시연에서 장치 연결/작업 시작·종료와 카메라·위치·장비 상태를 보여주는 흐름을 우선한다.
- 시연 마감과 운영 안정화가 충돌하면 시연 버전을 먼저 고정하되, 이를 현장 운영 합격으로 간주하지 않는다.
- 주 사용자는 현장 조사 직원이며 개발자/관리자가 초기 설정을 담당한다.
- 개선 우선순위는 **직원이 복잡한 설정 없이 연결하고 작업을 시작·종료하는 흐름**이 먼저이고, 그 다음이 수집 누락·저장 확인 고도화다.
- 현장 업무 완료 범위는 Jetson 저장 확인뿐 아니라 **서버 정상 수신 확인**까지다.
- 서버 데이터는 Jetson에 연결되지 않은 상태에서도 휴대전화 인터넷으로 조회할 수 있는 방향을 채택한다.
- 서버 보관함 1차 조회 범위는 작업/파일 목록, 수신 상태, 이미지·영상 미리보기와 경로 요약이다.
- 현장에서는 RTK·상태·실시간 결과를 우선 전달하고, 대용량 원본은 나중에 전송한다.
- 원본 업로드는 우선 사용자 승인형으로 시작하고, 검증 후 허용 네트워크 자동 전송을 검토한다.
- 지원 스마트폰은 지정 Android 기종부터 시작하고 **Android 태블릿을 포함**한다. iOS는 현재 범위에서 제외한다.
- Jetson은 **Orin NX 16GB 우선**, 이후 Xavier NX까지 확대한다.
- 여러 장치를 등록할 수 있지만 한 번에 하나를 선택해 운영하는 범위를 우선한다.
- 앱 제어 연결이 끊겨도 Jetson의 이미 시작한 수집은 계속되어야 한다. 재연결 후 장치 실제 상태를 기준으로 복구한다.
- 대표 사용 시나리오는 자전거 도로 조사다.
- 현재 실제 직원 사용 사례는 아직 없다. 사용성 기준은 실제 직원 시험으로 확인해야 한다.
- 작업은 프로젝트/조사 구간 아래 여러 실행을 묶는 구조를 우선한다.
- 현재 수집 필수 데이터는 검지 결과를 제외한 카메라/위치/IMU/깊이 등이다. 영상 항목은 실제 수집기가 이미지 프레임으로 저장하는지 기술 확인이 필요하다.
- 일반 현장 직원은 준비된 작업 몇 개 중 선택하며, 프로젝트/구간 정도만 입력하고 상세 설정은 관리자가 준비한다.
- 일시정지는 1차 필수 기능이 아니다. 종료 후 재시작하되 같은 프로젝트/구간으로 묶는다.
- 종료 후 저장 성공 여부·시간·용량·파일 수와 대표 미리보기를 우선 보여주고, 품질·서버 상태는 별도 상태로 보여준다.
- 데이터 탐색은 날짜/프로젝트/작업 중심으로 하고 파일/폴더 상세 탐색은 보조 기능으로 유지한다.
- UX는 현재 구조의 부분 손질이 아니라 **전체 화면 체계를 재설계하는 수준**으로 진행한다.
- 홈은 연결/준비/수집 상태와 다음 행동을 최우선으로 하고, 카메라·위치·최근 작업을 보조, CPU/GPU/온도는 상세로 둔다.
- 일반 작업 화면과 관리자/개발자 기능을 명확히 분리한다.
- 연결 복구 중에는 현재 화면을 유지하고 마지막 확인 시각과 불확실 상태를 표시한다.
- 연결·수집·인터넷·GNSS/RTK 상태를 분리해 보여준다.
- 위험 조작은 확인 절차를 사용하되, 삭제는 **이중 스와이프 방식 대신 1회 삭제 후 즉시 되돌리기 + 휴지통/소프트 삭제** 방향을 사용한다.
- 화면은 핵심 정보와 큰 조작을 우선하고 상세 정보는 펼치기 방식으로 둔다.
- 라이트/다크는 시스템 설정을 기본으로 따르고 사용자가 바꾸면 선택을 기억하는 방향이다.
- 중요 장애는 화면 표시와 함께 진동/소리를 선택적으로 사용한다.
- 수집 화면은 상태 중심이며 카메라/지도는 필요할 때 크게 연다.
- 처음 사용과 오류 안내는 현재 상황 + 다음 행동 + 단계별 도움을 제공한다.
- 기준 장치 센서 조합은 하나부터 시작한다.
- 스마트폰은 실제 사용자 기종 + 시험 기종을 우선 검증하며 Android 태블릿도 시험 목록에 포함한다.
- 연결은 상황별 기본 방식을 제안하고 실패 시 대안을 안내한다.
- 수집 프로그램 설치/업데이트는 1차로 관리자가 장치에 준비하고 앱은 등록·실행을 담당한다.
- 앱/Jetson 호환은 기본적으로 현재와 직전 승인 조합을 목표로 하되, 대규모 변경에서는 동일 승인 배포 조합만 보장할 수 있다.
- 개발/시험/운영 서버를 구분한다.
- 서버 오프라인 조회는 최근 작업 목록·수신 상태 캐시를 마지막 확인 시각과 함께 제공하는 방향이다.
- 수집 결과 소비자는 후처리 서버와 사내 GIS/분석 담당자다.
- 실행 조건 추적은 장치/작업자/시각 + 프로그램/설정/모델 버전 + 센서 품질까지 남기는 방향이다.
- 기존 데이터도 가능한 범위에서 새 목록에 노출하되 없는 메타데이터는 추정하지 않는다.
- 수집 중에는 수집과 상태 확인을 최우선으로 두고 무거운 업로드는 후순위로 둔다.
- 위치/RTK 시작 조건과 장애 정책은 작업 종류별로 구분한다.
- 수집 중 RTK 품질이 낮아져도 우선 계속 수집하고 문제 구간을 기록한다.
- 필수 센서 실패는 수집 중지, 선택 센서 실패는 경고 후 지속하는 방향이다.
- 모바일 RTK 경로 상실 정책은 작업 종류에 따라 구분한다.
- Jetson 재부팅 후 자동 재시작은 관리자 설정으로 둘 수 있으나 기본은 사람이 상태 확인 후 다시 시작하는 방향이다.
- 저장 공간 부족은 사전 경고 후 신규 시작 제한/안전 종료 정책을 우선한다.
- 발열/전원 문제는 보조 기능 축소 후 필요 시 안전 종료하고 위험 조건은 즉시 중단할 수 있어야 한다.
- 카메라 미리보기는 저지연 확인이 우선이다. Wi-Fi Direct 사용을 전제로 하므로 1차 요구에서 데이터 사용량 절감을 핵심 목표로 두지 않는다.
- 대표 연속 수집은 수 시간 단위로 본다.
- 누락/품질 저하 구간은 지도·작업 이력에 표시해 사용자가 재조사 여부를 판단할 수 있게 한다.
- RTK FIX 비율 등 품질 지표를 계산해 사용자가 이해하기 쉬운 요약으로 제공하되, 근거 없는 합격 임계값을 임의로 정하지 않는다.
- 현재 버전에서 외부 실시간 검지 기능 자체는 범위에서 제외하고 확장 방향으로만 둔다.
- 실제 실기 시험은 우선 PM/호스트가 수행한다.
- 데이터 손실·잘못된 장치 제어·인증 문제는 운영 배포 차단 사유다.
- 시험 증거는 시험표/결과/로그와 대표 정상·실패 화면 기록을 남긴다.
- 시작/중지 응답 유실 시 실제 상태 확인 후 사용자가 재시도를 결정한다.
- 같은 Jetson을 여러 휴대전화에 등록할 수 있으나 제어 담당은 한 번에 하나를 원칙으로 한다.
- 서버 직접 조회는 직원별 계정/권한 구조를 목표로 한다.
- 서버 데이터는 역할·프로젝트별 조회/다운로드/삭제 권한을 구분하는 방향이다.
- 서버 수신·무결성 확인 후 권한 있는 직원이 Jetson 원본을 삭제할 수 있는 정책을 우선한다.
- 서버 데이터 보관은 프로젝트 종료/납품 기준으로 관리하는 방향이다.
- 업데이트는 유휴 상태에서 관리자가 적용하는 방식으로 시작하고 이후 승인된 업데이트 흐름으로 확장한다.
- 현장 장애 지원은 직원 승인 후 제한된 원격 점검/유지보수를 허용하는 방향이다.
- 장애·작업 상태는 지정 사내 채널/업무 보드에 모으는 방향이다.

## 2. 명시적 후순위 Backlog

아래 항목은 이번 핵심 작업에서 구현을 강제하지 않는다. 설계가 깨지지 않도록 기록만 유지한다.

1. **실시간 검지 연동**: 검지 기능이 활성화되면 원본 전체가 아니라 검지된 사진과 메타데이터 중심으로 서버에 전송하는 기능.
2. **검사 구간 Geofence 자동 시작 보조**: 관리자가 검사 구간을 등록하고 휴대전화/장치가 해당 구간 근처에 도달했을 때 작업 시작을 제안하거나 조건에 따라 시작할 수 있는 기능. `geonova-depthai-mapper` 등 수집 저장소 변경도 필요하므로 별도 프로젝트 연동 과제로 관리한다.
3. Xavier NX 지원 확대.
4. 실사용 데이터 기반 RTK 품질 판정 기준 고도화.
5. 서버 수신 확인 후 허용 네트워크에서 원본 자동 업로드.

## 3. 에이전트 운영 모델

### 작업 에이전트
- 권장 모델: **GPT-5.6 Sol High 또는 XHigh**. 복합 구조 변경은 XHigh 우선.
- 각 에이전트는 지정 브랜치에서만 작업한다.
- 루트 `AGENTS.md`와 저장소 기존 계약을 따른다.
- 본인 소유 범위 밖 파일을 수정해야 하면 임의 수정하지 말고 실행 보고서에 `INTEGRATION_REQUEST`로 남긴다.
- 새 기능 구현뿐 아니라 관련 테스트와 검증까지 수행한다.
- 작업이 끝나면 반드시 `docs/agent-runs/AGENT_XX_EXECUTION_REPORT.md`를 남긴다.

### 검수 에이전트
- 요청 구성: **Astra XHigh**.
- 작업 브랜치와 기준 커밋을 비교하고 코드/문서/테스트를 검수한다.
- 기능을 직접 재작성하는 것이 아니라 결함·회귀·미검증 항목을 찾는다.
- 결과를 같은 브랜치의 `docs/agent-runs/AGENT_XX_ASTRA_REVIEW.md`에 남긴다.
- 판정은 `PASS`, `PASS_WITH_FIX`, `FAIL` 중 하나를 사용한다.
- `PASS_WITH_FIX` 또는 `FAIL`이면 해당 작업 에이전트가 같은 브랜치에서 수정 후 다시 검수한다.

### PM 평가 에이전트
- 7개 실행 보고서와 Astra 검수 결과를 읽는다.
- 요구사항 누락, 서로 충돌하는 구현, 통합 순서, 후속 작업을 평가한다.
- 결과를 merge-stage의 `docs/agent-runs/PM_CYCLE_XX_EVALUATION.md`에 남긴다.
- PM 에이전트는 검수 통과하지 않은 작업을 임의로 승인 완료 처리하지 않는다.
- 최종 승인자는 인간 PM/호스트다.

| AG07 | `work/07-qa-release-20260914` | 통합 QA 전략, CI 확대, 지원 매트릭스, 릴리스/롤백/실기 체크리스트 | `.github/workflows/**`, `scripts/**`, `docs/qa/**`, 독립 테스트 도구. 기능 코드 변경 금지 |

경로가 실제 저장소 구조와 다르면 에이전트는 먼저 조사해 가장 가까운 소유 영역으로 매핑한다. 다른 에이전트 소유 파일을 바꾸지 않는다.

## 5. 병렬 작업 원칙

- AG01은 다른 에이전트의 요구사항 계약을 정리하지만, 이미 확정된 PM 결정은 이 문서에 있으므로 모든 에이전트는 동시에 착수할 수 있다.
- AG02는 UI 표시 계층을 소유하며 네트워크/백엔드 로직을 구현하지 않는다. 필요한 상태/API는 mock 또는 인터페이스로 표현하고 `INTEGRATION_REQUEST`에 남긴다.
- AG03은 Android 연결 로직을 소유하고 Compose UI를 수정하지 않는다.
- AG04는 Jetson 실행·수집 로직을 소유하고 RTK 전용 코드와 삭제/휴지통 데이터 계약을 피한다.
- AG05는 서버/보관/삭제 생명주기를 소유한다. 사용자 계정/직접 서버 접근은 기존 인증 구조를 먼저 조사하고 보안을 낮추는 우회 구현을 금지한다.
- AG06은 품질 지표를 계산하되 PM이 정하지 않은 합격 임계값을 하드코딩하지 않는다.
- AG07은 현재 기준선과 통합 후 검증 체계를 만든다. 아직 존재하지 않는 기능을 통과한 것처럼 표시하지 않는다.

## 7. Astra 검수 기준

Astra는 최소한 다음을 확인한다.

1. PM 결정과 구현이 일치하는가.
2. 에이전트가 소유 범위를 넘어 다른 영역을 무단 변경하지 않았는가.
3. 기존 기능의 제거·회귀가 없는가.
4. 시작/중지/재연결/오프라인/실패 상태가 추측으로 처리되지 않는가.
5. 보안·인증·비밀정보를 약화하지 않았는가.
6. 테스트가 실제 변경을 검증하는가.
7. 자동 테스트와 실장치 검증을 구분했는가.
8. `INTEGRATION_REQUEST`가 빠지지 않았는가.
9. 후순위 기능을 현재 구현 완료로 오해하게 만들지 않는가.

## 8. merge-stage 통합 순서

7개 브랜치를 동시에 `main`에 넣지 않는다.

1. merge-stage를 최신 `main`과 동기화한다.
2. AG01 문서 계약을 우선 반영한다.
3. AG04 Jetson runtime, AG05 server/storage, AG06 RTK/quality를 순차 반영한다.
4. AG03 Android connectivity를 반영한다.
5. AG02 UI를 반영하고 앞 단계의 실제 API/상태 모델에 맞춰 **통합 보정 전용 후속 커밋**을 수행한다.
6. AG07 QA/CI/release 변경을 반영한 뒤 통합된 경로에 맞춰 최종 조정한다.
7. 전체 Android build/lint/unit test, backend test, upload_receiver test, 디자인 토큰/대비 검사, 가능한 통합 테스트를 실행한다.
8. Astra XHigh로 merge-stage 전체 검수한다.
9. PM agent가 전체 요구사항-기능-검수 매트릭스를 평가한다.
10. 인간 PM/호스트가 앱 화면과 실제 장치를 최종 확인한다.
11. 승인 후에만 `main` 병합한다.
12. `main` 병합·검증 후 작업 브랜치 삭제 여부를 결정한다.

## 9. 시연 마감 기준 권장 일정

마감은 2026년 10월 중순으로 고정하고 기능 범위를 그 안에 맞춘다.

- **9/14~9/20**: 각 브랜치 1차 조사·구현/설계 및 실행 보고서, Astra 1차 검수.
- **9/21~9/30**: 지적사항 수정, 핵심 기능 2차, PM cycle 평가.
- **10/1~10/7**: merge-stage 1차 통합, 앱 전체 흐름/서버/수집 연동 조정.
- **10/8~10/12**: Android 휴대전화·태블릿 + Orin NX 실기 검증, 데모 자료 작성, 결함 수정.
- **10/13~10/15**: 시연 버전 동결. 치명적 결함 외 기능 추가 금지.
- **10/16~엑스포 전**: 시연 리허설·자료·백업 시나리오 중심. 운영용 차기 작업은 별도 후속 cycle로 진행.

이 일정은 작업량을 숨기기 위한 완료 보장이 아니라, 이미 정해진 시연 마감에서 역산한 **운영 기준**이다. 실제 장비·모델·서버 제약이 확인되면 PM cycle에서 범위를 줄인다.

## 11. 최종 승인 조건

시연용과 운영용 승인을 분리한다.

### 시연 승인
- 앱 핵심 흐름이 끊기지 않고 설명 가능하다.
- 연결/작업/상태 화면의 정상·실패·오프라인 상태가 명확하다.
- 준비된 데모 데이터와 실제 데이터가 혼동되지 않는다.
- 데모 실패 시 사용할 대체 녹화/샘플 흐름이 준비되어 있다.

### 내부 운영 승인
- 데이터 손실·잘못된 장치 제어·인증 관련 차단 이슈가 없다.
- Android 지원 기종/태블릿과 Orin NX에서 지정 실기 시나리오가 검증된다.
- 앱 연결 단절 중 Jetson 수집 지속 및 재연결 후 실제 상태 복구가 검증된다.
- 저장 결과와 서버 수신 상태가 구분되어 확인된다.
- 서버 직접 조회 권한과 데이터 접근 정책이 검증된다.
- 롤백·진단 증거 수집 경로가 준비된다.

최종 제품 승인자는 인간 PM/호스트다.
