## 0. 먼저 읽을 것: 이번 지시의 의미와 확인 범위

### 0.1 이전 지침보다 넓어진 변경 권한

사용자는 기존 디자인을 보존하는 소규모 개선보다, 필요하다면 전반적인 디자인 리빌딩을 원한다. 기능도 새 UI에 다시 연결해도 괜찮으며, 사용 경험에 도움이 되는 기능 추가와 불필요한 부분 제거를 허용했다.

따라서 이전 `JETSONCONTROLLER_UI_UX_REDESIGN_AGENT.md`의 **“기존 화면 구조를 유지하며 단계적으로만 개선한다”는 제한은 이번 작업에 적용하지 않는다.** 기존 화면 배치·탭 개수·카드 모양·메뉴 명칭·화면 파일을 지켜야 할 이유는 없다. 색상만 바꾸고 끝내지 않는다.

다만 “기능은 다시 붙이면 된다”는 말은 **등록 정보, 인증 키, 측정 파일, 사용자 초안, 실제 장비의 안전장치를 지워도 된다는 뜻이 아니다.** 화면 교체와 데이터 파괴를 구분한다. 기존 통신·서비스 계층을 우선 재사용하면 UI를 크게 바꾸면서도 기능 재연결의 위험을 줄일 수 있다.

이 문서는 **디자인 설계 및 후속 구현 지시서**다. 문서 작성 단계에서 앱을 수정·빌드·설치하거나 실기기 검증을 완료한 것이 아니다. 에이전트는 아래 설계를 실제 앱에 구현하고 검증하는 역할을 맡는다.

### 0.2 공유한 Claude 디자인: 참고 대상이지만 아직 미확인

사용자 지정 참고 디자인:

`https://claude.ai/code/artifact/e06fb33d-b2fb-4cb3-b8c6-565ac5adaa95`

문서 작성 환경에서는 이 URL의 실제 화면·코드를 불러오지 못했다. 로그인 필요 여부나 원본 내용은 확인하지 못했다. **아래 팔레트·4탭 구조·와이어프레임은 해당 원본을 관찰하거나 복제한 결과가 아니라, 현재 앱 코드와 사용자 요구를 토대로 제안한 독립 재설계안이다.**

실행 에이전트는 사용 가능한 정상 접근 수단으로 원본을 먼저 확인한다. URL, 사용자가 제공한 스크린샷, 내보낸 HTML/React 코드 중 실제 확보한 자료만 근거로 삼는다. 인증 우회, 로그인 정보 추측, 다른 비공개 artifact 검색은 하지 않는다.

| 상태 | 행동 |
|---|---|
| 원본 확인 가능 | 대표 화면과 상태를 캡처하고 색상·위계·탭·카드·버튼·문구를 관찰한다. 아래 설계와 비교해 사용자 의도를 잘 살리는 요소를 채택한다. |
| 일부 화면만 확인 | 확인한 부분과 확인하지 못한 부분을 구분한다. 정지 이미지로 버튼 동작이나 API를 추정하지 않는다. |
| 원본 계속 접근 불가 | `REFERENCE_UNVERIFIED`로 기록하고 아래 재설계안으로 독립 작업을 계속한다. 원본 반영·원본 일치라고 보고하지 않는다. |

결과 보고서에는 `참고 요소 → 채택/변형/제외 → 이유 → 구현 화면`의 대조표를 남긴다. 미확인 상태에서는 대조표를 허구로 채우지 않는다. 참고 디자인이 나중에 확보되더라도 검증된 기능·접근성·데이터 상태를 시각적 유사성 때문에 퇴행시키지 않는다.

### 0.3 판단 우선순위

**사용자의 최신 요구 → 실제 장치와 API의 사실 → 안전·데이터 무결성 → 사용자 작업 흐름 → 참고 디자인의 의도 → 이 문서의 기본 시각안 → 기존 화면 형태.**

디자인 선택은 스스로 한다. 매 화면마다 사용자에게 색상이나 카드 배치를 고르게 하지 않는다. 다만 승인되지 않은 전원 종료, 네트워크 변경, 데이터 삭제까지 자율 디자인의 범위로 해석하지 않는다.

## 1. 제품 방향: 장비 관리 메뉴가 아니라 현장 작업 도구

### 1.1 핵심 경험

사용자가 앱을 열었을 때 다음 순서로 이해하게 만든다.

**어떤 장비인가 → 지금 무엇을 할 수 있는가 → 무슨 작업이 진행 중인가 → 영상·위치는 정상인가 → 결과는 어디에 있는가.**

한 문장 방향은 **“장비를 연결하고, 작업을 실행하고, 현장에서 확인한 뒤, 결과를 가져오는 앱”**이다. 서버 관리자 화면을 스마트폰에 축소한 모양이나 의미 없는 분석 대시보드를 만들지 않는다.

### 1.2 성공 기준: 설계 목표이며 아직 측정한 성과가 아님

- 장비가 선택되어 있고 연결이 검증된 일반 상태에서 현재 작업을 첫 화면에서 확인한다.
- 현장 화면에서 영상 또는 GNSS 상세를 한 번의 탭으로 연다.
- 이미 선택한 작업의 실행 요청은 통상 두 번 이하의 탭으로 접근한다. 장비 확인·필수 권한·안전 확인이 필요한 경우 이를 생략하지 않는다.
- 작업 상세에서 연결된 결과 폴더를 한 번에 연다. 결과 연결 정보가 없으면 없는 이유를 보여준다.
- 문제가 나면 오류 코드보다 “무엇이 안 되는지 / 다음에 무엇을 할지”가 먼저 보인다.
- 첫 화면에 정상 상태 카드, 기술 정보, 설정 버튼이 여러 층으로 쌓이지 않는다.

실제 사용자 시험을 하지 않았다면 “사용 시간이 몇 % 단축되었다”처럼 성과를 만들어 쓰지 않는다.

### 1.3 무엇을 리빌딩하고 무엇을 재사용하는가

| 구분 | 이번 결정 |
|---|---|
| 화면·정보 구조·주 내비게이션 | 전면 리빌딩 허용. 아래 4탭 기본안을 채택한다. |
| 디자인 토큰·공통 컴포넌트 | 기존 구현을 정리하거나 교체한다. 구형·신형 스타일을 섞지 않는다. |
| Screen/Route/ViewModel의 UI 책임 | 필요하면 분리·재작성한다. 기능 단위로 재연결한다. |
| Kotlin·Compose·Material 3 | 기존 네이티브 기반을 유지한다. HTML 시안을 WebView로 제품화하지 않는다. |
| Repository·transport·서비스·API | 검증된 기능을 새 UI에 연결하는 기본 자산으로 사용한다. UI만 바꾸려다 모두 재작성하지 않는다. |
| 중복·불필요한 화면/기능 | 실제 사용 경로·대체 경로를 확인한 후 통합 또는 제거한다. §4의 기준을 따른다. |
| 인증·등록·파일·사용자 설정·안전 확인 | 보존한다. 스키마를 바꾸면 마이그레이션과 복구 검증을 포함한다. |

Compose/Material 3, 기존 UI 컴포넌트와 연결 정책이 있는 것은 코드 관찰이다. 4탭 구조와 화면 역할은 이번 설계 결정이다. [기술 기반][R2] · [기존 화면 연결][R3]

## 3. 먼저 확인하고 작업을 시작한다

### 3.1 변경 전 기준점

현재 디렉터리와 적용되는 `AGENTS.md`를 확인하고 다음 읽기 작업을 수행한다.

```bash
git status --short
git branch --show-current
git rev-parse HEAD
git log -5 --oneline
```

이 MD의 실제 경로를 기록한다. 기존 사용자 변경, 연결 안정성 수정, 미완료 작업, 이미 도입된 새 UI를 목록화한다. 사용자 변경을 자동 stash하거나 덮어쓰지 않는다. `reset --hard`, `clean -fd`, 강제 푸시를 사용하지 않는다. 별도 브랜치/체크포인트를 기존 저장소 운영 방식에 맞춰 사용한다.

현재 앱의 진입점·화면별 책임·상태 소유자·서비스 호출을 확인하고 아래 표를 결과 보고서에 작성한다.

`기존 기능 → 현재 코드 → 새 화면 → 연결할 상태/콜백 → 유지/이동/통합/삭제 → 검증 방법`

### 3.2 실제 환경과 디자인 작업을 불필요하게 묶지 않는다

휴대전화의 모델·Android 버전·화면 배율·설치 앱·ADB serial, 사용 가능한 Jetson 연결·서비스·지원 API를 확인한다. 현재 진행 중인 수집·업로드·RTK 중계가 있는지도 확인한다. 여러 장치 중 임의의 첫 장치에 설치하지 않는다.

**실기기에 접근하지 못해도 디자인 토큰, 새 화면, Preview, debug용 디자인 검증 화면, 단위 테스트는 진행한다.** 실기기 부재를 이유로 보고서만 만들고 멈추지 않는다. 반대로 Preview 성공을 Wi-Fi Direct·BLE·RTK의 실기 검증으로 대체하지 않는다.

### 3.3 기준 화면과 사용자 흐름

가능하면 다음을 변경 전에 캡처한다: 장비 등록 전, 장비 선택, 연결 중/실패, 홈, 작업 목록/상세, 데이터, 센서·영상, 설정·알림. 같은 테스트 장비·데이터·글꼴 설정으로 변경 후 비교한다. 캡처하지 못했다면 그 사유를 기록한다.

원본 artifact도 확보했다면 앱과 같은 폭으로 비교한다. 실제 장비 번호·정확한 위치·QR 인증 문자열·비밀번호는 공유 캡처에서 마스킹한다. 캡처를 예쁘게 만들기 위해 정상 상태를 조작하지 않는다.

## 4. 기능과 UI의 유지·추가·삭제 결정

### 4.1 반드시 새 UI에 연결할 핵심 가치

장비 등록·선택·연결, 현재 장비의 실제 상태, 작업 실행·중지와 결과 접근, 장비 데이터 조회, 지원되는 서버 업로드, 카메라 확인, GNSS/RTK·센서 확인, 문제 안내·복구, 필요한 설정·알림은 새 경험에서 사용할 수 있어야 한다. 기존의 모든 버튼 위치나 독립 화면을 유지할 필요는 없다.

### 4.2 이번에 추가할 UX 기능

| ID | 추가할 것 | 사용자 이익 | 구현 범위 |
|---|---|---|---|
| A01 | 선택 작업 기준 준비 확인 | 실행 전에 어떤 조건이 부족한지 이해 | 현재 상태·capabilities·설정에서 산출. 새로운 장치 점검 프로토콜을 발명하지 않음. |
| A02 | 최근 선택 작업 바로 열기 | 매번 작업 목록에서 찾지 않음 | 장비별 안정 ID를 저장. 자동 실행이나 과거 명령 재전송은 금지. |
| A03 | 현장 집중 화면 | 영상 또는 지도와 작업 상태를 한 곳에서 확인 | 기존 영상/지도와 연결. 동시에 여러 고부하 뷰를 실행하지 않음. |
| A04 | 마지막 수신 시점 표시 | 멈춘 영상·오래된 위치를 현재로 오해하지 않음 | 기존 revision·시각·freshness 재사용. 실제 미제공 값은 확인 불가. |
| A05 | 작업 → 결과 → 전송 연결 | 폴더를 처음부터 다시 찾지 않음 | 기존 outputRootId/outputPath 등 확인된 연결 정보 사용. 추정 매칭 금지. |
| A06 | 끊겨도 화면·초안 유지 | 재연결 때문에 작업 문맥을 잃지 않음 | 화면 상태 저장, 읽기 전용 제한, 기존 복구 정책 연결. |
| A07 | 상태별 문제 해결 진입점 | 기술 방식을 몰라도 다음 행동을 찾음 | 권한·등록·제어 연결·인터넷 경로를 분리해서 안내. |
| A08 | 장비별 선택·표시 설정 | 여러 장비의 최근 작업과 화면 상태가 섞이지 않음 | 기존 저장 수단 재사용. 데이터 구조 변경은 최소화. |

A01~A08은 기본 범위다. 실제 계약 부재로 구현할 수 없는 부분은 §13의 대안으로 바꾸고 이유를 기록한다. **사용자 기능을 추가한다는 이유로 존재하지 않는 원격 API까지 만들 필요는 없다.**

장비 별칭, 상세 진단 정보의 수동 공유는 여력이 있고 기존 저장/공유 구조에 자연스럽게 붙는 경우만 추가한다. 개인정보를 기본 수집하거나 자동 외부 업로드하지 않는다.

### 4.3 제거·통합할 것: 화면 제거와 능력 제거를 구별

| 대상 | 결정 | 새 위치/대안 |
|---|---|---|
| 기존 센서 독립 하단 탭 | 탭 제거·기능 통합 | 현장의 영상/위치 바로가기 + 장비 상세의 센서 전체 상태 |
| 기존 알림/설정 하단 탭 | 탭 제거·역할 분리 | 상단 종: 알림 목록 / 장비 탭의 앱 설정: 알림 설정 |
| 홈의 팬·재부팅·종료·네트워크 설정 | 홈에서 제거 | 장비 상세 → 제어·설정. 전원 확인은 유지 |
| 정상 상태를 크게 반복하는 안내 | 상시 대형 카드 제거 | 장비 헤더의 짧은 상태, 필요할 때 상세 |
| 작업 카드의 등록 해제 아이콘 | 목록에서 제거 | 작업 상세 → 더보기 → 등록 해제 |
| 작업 목록의 부팅 시 실행·원문 로그·고급 설정 | 목록에서 제거 | 상세의 설정/고급 관리 |
| 같은 기능으로 가는 반복 메뉴·중복 화면 | 경로 통합 후 구형 UI 제거 | 표준 진입점과 기존 링크의 새 목적지 매핑 |
| 지속적인 성공 토스트·단순 정상 알림 | 반복 표시 제거 | 최초 완료 피드백 또는 이력, 변화 없는 상태는 조용히 유지 |
| 의미 없는 장식 차트·가짜 수치·미구현 기능 타일 | 발견하면 제거 | 현재 동작하는 기능만 제품 UI에 표시 |
| 반복 강제 온보딩·첫 화면에서 기술 방식 고르기 | 기본 흐름에서 제거 | 최초 등록 시 필요한 안내, 연결 방식은 문제 해결에서 제공 |

위 항목은 모두 현재 존재한다고 단정하는 목록이 아니다. 일부는 작업 중 발견하면 적용할 제거 기준이다.

화면 외의 실제 기능을 폐기할 수 있는 조건은 **사용자 가치가 중복되거나 사라졌고, 대체 동선 또는 명확한 제외 근거가 있으며, 사용자 데이터·핵심 제어·안전 기능에 손실이 없을 때**다. 빈 버튼을 남겨두거나 “다시 붙이면 된다”는 이유로 핵심 기능을 미연결 상태로 납품하지 않는다. 폐기한 기능은 이유와 영향을 결과표에 명시한다.

### 4.4 이번에 만들지 않을 것

새 계정·조직·프로젝트 관리 시스템, AI 채팅, 3D 장비 모델, 커스텀 대시보드 편집기, 실시간 분석 플랫폼, 새 지도 엔진, 네트워크 프로토콜 전면 재작성은 범위 밖이다. 배터리 잔량·정확한 작업별 수집량·검출 수·일시정지·전송 이어받기는 장비/API가 실제 제공할 때만 노출한다. 일반 Python 작업을 임의로 “측정 세션”이나 “녹화”로 바꾸지 않는다.

## 5. 새 정보 구조: 현장 / 작업 / 데이터 / 장비

```text
앱 시작
├─ 등록된 장비 없음 → 첫 장비 등록 → QR 또는 기존 수동 등록 대안
└─ 등록 장비 있음 → 마지막 선택 장비의 현장 화면
                    (선택은 복원, 연결·작업 상태는 재확인)

[현장]  현재 장비 · 준비 확인 · 진행 작업 · 영상/위치 바로가기
  ├─ 준비 확인 상세
  ├─ 현장 집중 → 영상 / 위치 중 하나
  └─ 진행 작업 상세 / 연결된 결과

[작업]  실행 중 / 등록된 작업 / 최근 선택
  ├─ 작업 상세 → 실행·중지·결과
  └─ 작업 추가·설정·로그·고급 관리

[데이터]  장비 파일 / 전송 / 서버
  ├─ 폴더·검색·선택
  └─ 전송 확인·진행·실패 상세

[장비]  선택 장비 · 다른 장비 · 연결 및 센서 · 관리
  ├─ 장비 등록·선택·연결 문제 해결
  ├─ 장비 상세 → 네트워크·센서·저장소·팬·전원
  └─ 앱 설정 → 테마·알림·앱 정보 (연결 없이 접근 가능)

공통 상단: 장비 선택 + 장비 문맥 + 알림 목록
전체 화면/편집/등록: 뒤로가기 + 제목, 필요하면 하단 탭 숨김
```

이 4탭안은 원본 artifact와 실사용 검토에서 더 나은 근거가 나오면 조정할 수 있다. 단, 탭 숫자를 줄였다는 이유로 성공 처리하지 않는다. 센서 확인이나 작업 중지가 더 깊어지면 바로 수정한다.

### 5.1 장비 문맥을 잃지 않게 한다

현장·작업·데이터는 선택 장비를 대상으로 한다. 장비 이름을 누르면 장비 선택 sheet를 열고, `모든 장비 관리`로 장비 탭에 연결한다. 장비가 한 대여도 이름과 연결 상태를 숨기지 않는다.

장비 선택과 제어 연결은 같은 사건이 아니다. 장비 카드 열람만으로 현재 연결을 끊거나 다른 장비의 작업을 중단하지 않는다. 실제 전환이 기존 연결/중계에 영향을 주면 명시적인 `이 장비로 전환` 행동과 영향 안내를 제공한다. 명령 실행 시 UI가 기억하는 장비 ID와 현재 제어 대상이 같은지 재확인한다.

### 5.2 연결이 없어도 앱 전체를 잠그지 않는다

등록 정보, 앱 설정, 이미 확보한 이력·메타데이터는 접근 가능하게 한다. 실제 파일 내용이 캐시에 없으면 조회 가능하다고 표시하지 않는다. 장비 제어만 제한하고 이유·복구 행동을 보여준다. 장비 없는 상태에서 회색 버튼 수십 개가 있는 대시보드를 보여주지 않는다.

### 5.3 내비게이션 계약

주 탭의 선택·스크롤·입력 상태를 보존하고 같은 탭 재선택으로 화면이 중복 쌓이지 않게 한다. 장비 ID를 상태 키에 포함한다. 전체 화면 영상이나 지도에서 뒤로 가면 진입했던 탭·작업 문맥으로 돌아간다. 뒤로가기·탭 이동·화면 회전은 장비 연결 해제 명령이 아니다.

기존 알림 목적지와 내부 route를 새 목적지로 매핑한다. `ControlSection` 순서 번호나 표시 문구가 저장 키로 쓰이는지 확인한 뒤 변경한다. 단순 이름 교체로 저장 상태나 알림 이동을 깨뜨리지 않는다. 내비게이션 저장·복원은 설치된 버전의 API를 사용한다. [A4], [A5]

## 6. 시각 디자인 시스템

### 6.1 기본안: 차분한 현장 콘솔

**밝은 중성 바탕 + 선명한 타이포그래피 + 깊은 청록색 주 행동 + 짧은 상태 표시.** 정상 화면은 차분하고, 사용자 행동과 문제만 대비가 커진다. 다크 테마는 동일한 구조와 의미를 유지한다. 시스템 테마를 기본으로 하고 앱 설정에서 선택할 수 있게 한다.

기존 앱과의 차이는 팔레트보다 **정보 우선순위, 작업 중심의 첫 화면, 4탭 구조, 낮은 반복 밀도, 통일된 조작 방식**에서 나와야 한다. 색을 다르게 칠하는 것만으로 리빌딩을 대신하지 않는다.

참고 artifact를 확보했다면 해당 디자인의 시각적 의도를 우선 대조한다. 아래 값은 접근 불가 상황에서도 구현을 시작할 수 있는 기본값이다. 기존 상표·앱 이름·로고는 임의로 새 브랜드로 바꾸지 않는다.

### 6.2 색상 토큰

아래는 설계 제안값이다. 각 화면에서 직접 색을 지정하지 말고 역할별 토큰으로 사용한다. 현재 Material 버전에서 사용하는 container/on-container, surface, inverse, outline 역할까지 정리한다. 일부 색만 바꾸고 나머지 기본 팔레트가 섞이게 두지 않는다. Material 3의 색상·타이포·shape 체계를 기반으로 구현한다. [A1]

텍스트 대비는 일반 4.5:1, 큰 텍스트는 적용 조건에 맞춰 3:1 이상을 목표로 검증한다. 조작과 상태를 구별하는 비텍스트 요소도 3:1 기준을 점검한다. WCAG 기준을 검증 참고값으로 사용하되 이 문서만으로 네이티브 앱 전체의 인증·준수를 선언하지 않는다. [A2], [A3]

### 6.4 컴포넌트 계약

기존 `AppBanner`, `StatusBadge`, `AppSpacing`을 리팩터링하거나 다음 역할로 교체한다. 이름은 제안이며 실제 레포 관례에 맞춰도 된다. 기존 컴포넌트와 동일한 기능의 두 번째 체계를 만들지 않는다.

| 컴포넌트 | 책임 | 필수 상태 |
|---|---|---|
| `AppShell` | 탭·헤더·insets·Snackbar의 공통 소유 | 일반/전체 화면/오프라인 |
| `DeviceContextHeader` | 장비 이름·연결 상태·장비 선택·알림 | 미선택/확인 중/제어 가능/제한/끊김 |
| `CurrentWorkCard` | 선택 또는 진행 작업·주 행동 | 없음/준비/시작 요청/실행/중지 요청/오류/확인 불가 |
| `ReadinessRow` | 조건·판정 근거·해결 행동 | 충족/부족/확인 불가/해당 없음 |
| `StatusBadge` | 짧은 상태 라벨과 의미 | 정상/주의/오류/정보/미확인 |
| `IssueBanner` | 현재 동선을 막는 문제 하나와 행동 | 권한/인증/연결/실패 |
| `UnavailableState` | 비활성 이유와 가능한 다음 행동 | 미지원/미설정/연결 필요/권한 필요 |
| `DataRow` | 파일·폴더·위치·선택 | 일반/선택/캐시/조회 불가 |
| `TransferRow` | 파일 전송 상태와 실제 진행량 | 대기/전송/완료/실패/취소 요청 |
| `DangerActionDialog` | 대상·영향·확인 행동 | 중지/재시작/등록 해제/전원 |

상태별 Preview와 접근성 의미를 같이 구현한다. 컴포넌트가 네트워크 연결이나 작업 시작을 직접 소유하지 않게 한다.

### 6.5 가벼운 구현 규칙

스크롤·탭·버튼 피드백은 기본 Compose/Material 동작을 활용한다. 필요할 때 120~200ms 정도의 짧은 전환을 사용하되 이는 권고값이며 필수 애니메이션이 아니다. 모션 축소·시스템 애니메이션 설정을 존중한다.

블러, 유리 효과, 패럴랙스, 계속 움직이는 배경, 대형 Lottie, 커스텀 차트 라이브러리, 화면 전체 shimmer는 추가하지 않는다. 새 런타임 UI 의존성은 기본 0개를 목표로 한다. 필요한 예외는 목적·용량·유지 비용을 기록한다.

성능은 실제 빌드에서 확인한다. Compose의 상태 읽기 범위를 좁히고, 비용 큰 계산을 렌더링 본문에서 반복하지 않으며, 긴 목록은 안정 키가 있는 lazy 목록으로 구성한다. 고빈도 영상·센서 변화가 앱 전체를 다시 그리게 하지 않는다. [A6]

## 7. 화면별 구현 명세와 와이어프레임

아래 텍스트 배치는 **독립 재설계안의 구조 명세**다. 원본 artifact의 캡처가 아니다. 예시 문구를 실제 데이터처럼 하드코딩하지 않는다. 화면 높이 수치는 강제하지 않고 폰트 배율·insets에 따라 늘어나게 한다.

### 7.1 첫 등록·장비 선택

첫 사용에는 장비 그림·홍보 문구보다 `장비 등록`이라는 단일 주 행동을 보여준다. `QR로 등록`을 중심으로 기존 수동 등록 대안을 유지한다. 카메라·근처 기기 등 권한은 해당 기능을 요청하는 시점에 설명하고 요청한다. 필요하지 않은 권한을 시작 화면에서 한꺼번에 받지 않는다.

등록 이후에는 긴 환영 화면을 반복하지 않는다. 마지막 선택 장비를 복원하되 `연결 확인 중`에서 실제 상태 확인을 거친다. 여러 장비는 목록에서 이름·현재 연결 관계·다음 행동을 비교하게 한다. 마지막에 저장한 장비를 자동으로 “온라인”이라 표시하지 않는다.

**완료 조건:** QR 거절/실패/수동 입력/등록 성공/등록 후 연결 실패가 서로 다른 다음 행동을 제공한다. 장비 등록이 연결·작업 실행까지 성공했다는 의미가 되지 않는다.

### 7.2 현장 — 기본 진입 화면

```text
[선택 장비 이름 ▾]                         [알림]
 제어 가능 · 연결 방식 / 또는 연결 확인 중

[필요할 때만: 지금 해결해야 할 문제 + 해결 행동]

현재 작업
┌──────────────────────────────────────────┐
│ 작업 이름                         상태   │
│ 시작 시각 또는 확인 가능한 짧은 설명      │
│ [현재 상태에 맞는 주 행동]   [작업 상세]  │
└──────────────────────────────────────────┘

준비 확인                       [자세히]
장비 제어 / 저장공간 / 선택 작업의 필요 조건

[영상 확인]                    [위치 확인]
각 항목은 마지막 수신·가용성을 짧게 표시

최근 결과 또는 전송 요약       [데이터 보기]

[현장]       [작업]       [데이터]       [장비]
```

**정렬 원칙:** 조치가 필요한 문제 → 현재/선택 작업 → 필요한 준비 상태 → 영상·위치 → 결과. 정상 상태에서는 작은 헤더 상태만 유지하고 대형 “모두 정상” 카드를 넣지 않는다.

작업이 없으면 `작업 선택`, 선택했으면 `실행 준비 확인` 또는 안전한 조건의 `작업 시작`, 실행 중이면 `현장 집중`을 주 행동으로 둔다. 실행 중지 버튼도 찾을 수 있는 위치에 유지하되 시작과 같은 위치의 무확인 토글로 만들지 않는다. 두 액션이 서로 가려지지 않게 한다.

여러 작업이 실행 중일 수 있으면 이를 한 작업으로 축소하지 않는다. 대표 작업은 사용자가 고른 작업 또는 명확한 선택 기준으로 표시하고 `그 외 실행 중 N개`로 목록에 연결한다. “현재 작업”을 전역 단일 작업 모델로 바꾸지 않는다.

카메라 썸네일은 이미 받은 프레임이 있을 때 선택적으로 쓰며, 홈 진입만으로 새 영상 스트림을 시작하지 않는다. 프레임이 없을 때 장식용 카메라 사진을 실제 영상처럼 보여주지 않는다. CPU/RAM/온도는 장비 상세로 옮기고 이상이 작업에 영향을 줄 때만 현장에 올린다.

**완료 조건:** 일반 화면에서 작업·연결·다음 행동이 읽히며, 폰트 확대 시에도 주 행동이 스크롤로 도달 가능하고 하단 메뉴 뒤에 가려지지 않는다.

### 7.3 준비 확인 — 실행을 돕는 점검, 새로운 장애물이 아님

작업별 필수 조건만 보여준다. 각 행은 `무엇 / 상태 / 근거 / 해결 행동`으로 구성한다. 현재 데이터가 없으면 `확인 불가`다. 선택 작업의 센서 요구사항이 정의되지 않았다면 GNSS·RTK·IMU를 모두 필수로 추정하지 않는다.

**시작 전 조건과 실행 후 수신 상태를 분리한다.** 작업이 카메라를 기동하는 구조라면 “아직 카메라 영상이 없음”을 작업 시작 차단 조건으로 만들지 않는다. 시작 이후 해당 센서가 실제 활성·수신으로 바뀌는지를 확인한다.

필수 조건 실패는 해당 명령을 제한하고 이유를 표시한다. 단순 권고는 경고로 안내하며 기존 정책상 가능한 실행을 임의로 막지 않는다. 점검 결과를 백분율이나 가짜 진행률로 표시하지 않는다. 매 실행마다 동일한 체크리스트를 반복 확인시키지 말고 선택·설정·상태 변화에 따라 갱신한다.

### 7.4 작업 목록·상세·추가

목록은 작업명, 상태, 한 줄 설명, 결과 유무를 보여준다. 카드 전체는 상세 진입이며 동시에 카드 안의 시작 버튼과 같은 동작을 중복 수행하지 않는다. 검색은 목록 규모와 기존 데이터 구조에 맞춰 제공한다. `작업 추가`는 별도 주 행동으로 두되 진행 중 작업보다 강조하지 않는다.

```text
작업 상세
[뒤로] 작업 이름                    [더보기]
상태 · 적용 장비

실행 상태 / 문제 / 확인 가능한 시작 시각
[작업 시작 또는 중지]                [결과 보기]

기본 설정 요약                      [설정 변경]
관련 센서 상태                      [현장 집중]

[실행 로그 보기]
더보기: 고급 설정 / 부팅 시 실행 / 등록 해제
```

시작 버튼을 눌렀으면 즉시 `시작 요청 중` 피드백을 주고 실제 서비스 상태 확인 후 `실행 중`으로 바꾼다. 응답이 없을 때 성공으로 낙관 변경하지 않는다. 중지·재시작은 현재 실행과 데이터 영향에 맞는 확인을 거친다. 지원하지 않는 일시정지·재개 버튼은 넣지 않는다.

부팅 시 실행은 별도 설정이며 현재 작업의 실행 상태와 혼동하지 않는다. 등록 해제는 파일 삭제와 구별한다. 편집 화면은 필수 입력부터 노출하고 YAML·경로·고급 파라미터는 고급 구역으로 분리한다. 초안은 장비·작업별로 보존한다.

**완료 조건:** 실행/중지의 중복 탭이 중복 요청을 만들지 않으며, 같은 이름의 다른 장비 작업에 명령이 전달되지 않는다. 작업이 종료됐다는 사실과 결과 파일이 검증됐다는 사실을 구분한다.

### 7.5 현장 집중 — 영상과 위치를 편하게 확인

```text
[뒤로] 선택 장비 · 작업 이름          [문제]
[영상] [위치]            수신 상태·마지막 갱신

              주 콘텐츠 영역
     영상: 비율 유지 / 위치: 기존 지도

상태 요약: 작업 상태 · 필요한 GNSS/RTK 상태
[작업 상세]                          [중지]
```

영상·위치는 한 번에 하나를 중심으로 보여준다. 큰 화면에서만 실측 성능이 충분하고 사용자 이득이 있을 때 분할한다. 화면 회전으로 영상·지도 인스턴스나 네트워크 수집기가 중복되지 않게 한다. 화면 켜짐 유지는 이 화면의 사용자 선택으로만 적용하고 이탈 시 해제한다. 휴대전화 화면 이탈이 Jetson의 수집 작업 중지로 이어지면 안 된다.

**영상 상태:** `첫 프레임 대기 / 영상 수신 중 / 갱신 지연 / 마지막 화면 / 사용 불가`를 구분한다. 현재 코드의 `updatedAtEpochMillis`는 새 프레임을 처리한 휴대전화 측 시각이므로 이를 촬영 시각이나 end-to-end 지연으로 부르지 않는다. 같은 revision을 다시 받았다고 프레임의 최신성이 갱신되는 것으로 처리하지 않는다. [R8], [R9]

`LIVE`를 사용한다면 최근 새 프레임 수신 근거가 있을 때만 사용한다. 오류가 있는데 이전 프레임이 남은 경우에는 영상 위에 `마지막 수신 화면 · 갱신 지연`을 표시한다. 센서 활성·HTTP 성공·영상 프레임 갱신은 각각 다른 사실이다. 낮은 프레임 주기의 장비에 고정된 임의 지연 기준을 적용해 정상 화면을 오류로 만들지 않는다.

네트워크 재시도·visibility·mutex는 기존 구현을 먼저 검토한다. 카메라 기동/종료를 UI 편의만으로 추가 실행하지 않는다. 후처리 마스크·탐지 박스·탐지 건수는 같은 프레임의 실제 데이터와 대응할 때만 제공한다.

### 7.6 위치·GNSS·RTK

기존 지도와 공급자 설정을 재사용한다. 지도 아래 또는 펼침 패널에 위치 출처, 갱신 시점, GNSS 수신 상태, RTK 상태, 제공되는 정확도 값을 배치한다. 지도를 가리는 상시 정보 카드 더미를 만들지 않는다.

`Jetson GNSS 위치`와 `휴대전화 위치`를 명시적으로 구분한다. 장비 신호가 끊겼다고 휴대전화 위치를 동일한 장비 마커로 자동 대체하지 않는다. 마지막 장비 위치는 오래된 데이터로 구별한다. 지도 타일을 못 가져오는 상황과 GNSS 위치를 못 받는 상황도 분리한다.

NTRIP 연결, 보정 데이터 수신·중계, 수신기의 RTK FIX는 동의어가 아니다. `보정 데이터 전달 중`만 확인했다고 `RTK 고정`으로 표시하지 않는다. `RTK FIX/FLOAT`는 원래 상태와 쉬운 설명을 함께 보여주고, 정확도 수치가 없으면 임의로 cm 단위를 만들지 않는다.

**완료 조건:** 휴대전화 위치만 가능한 경우, 장비 GNSS 미수신, RTK FLOAT, 보정 전송 중이지만 FIX 아님, 지도 네트워크 실패가 서로 구별된다.

### 7.7 데이터·전송

상단은 `장비 파일 / 전송 / 서버`로 구분한다. 장비 파일과 서버 파일을 하나의 출처 없는 목록으로 섞지 않는다. 위치 경로는 짧은 breadcrumb를 기본으로 하되 필요한 전체 경로는 상세에서 확인한다.

파일/폴더는 이름·종류·크기·확인 가능한 시각을 보여주는 목록으로 만든다. 날짜별 수집 세션이나 작업별 그룹은 실제 메타데이터가 있을 때만 사용한다. 최근 파일을 최근 작업의 결과라고 추정하지 않는다. 폴더, 검색, 정렬, 선택 상태는 장비별로 보존한다.

전송 확인 화면에는 `어느 장비의 무엇을 / 어느 서버로 / 알려진 용량 / 실행 가능한 연결 조건`을 표시한다. 지원되는 범위에서 단건과 선택 항목 전송을 제공한다. 총량을 모르면 백분율 대신 처리 항목 수·대기 상태 등 확인 가능한 정보만 보여준다.

**중요:** 현재 코드의 서버 업로드 시작은 LAN만 허용한다. Wi-Fi Direct 상태에서 업로드 불가 이유와 LAN 전환 안내를 제공한다. 휴대전화 인터넷 연결 또는 모바일 RTK 중계가 있다는 이유로 이 제한을 UI에서 해제하지 않는다. 실제 백엔드 정책이 바뀌었다면 별도 확인 후 반영한다. [R11]

재시도·취소·이어받기는 서버 계약과 일치해야 한다. 취소 요청이 접수됐다고 취소 완료로 표시하지 않는다. 성공한 전송을 중복 재전송하거나 파일을 자동 삭제하지 않는다. 서버 저장소에 별도 자격증명이나 연결 조건이 있으면 그 조건으로 판정한다.

**완료 조건:** 캐시 메타데이터를 실제 다운로드된 파일로 오해하지 않으며, 실패 이력을 숨기지 않고 원인과 가능한 조치를 제공한다.

### 7.8 장비·설정

장비 탭 상단은 현재 선택 장비다. 그 아래에 다른 장비와 등록 진입점, 선택 장비의 센서·연결·관리 구역, 장비 연결 없이 접근 가능한 앱 설정을 둔다. 여러 장비가 있을 때 카드 선택과 실제 연결 전환의 차이를 명확히 한다.

장비 상세에는 네트워크, 전체 센서 상태, 저장공간, 시스템 지표를 우선 제공한다. 팬·전원·고급 진단은 하단 관리 구역으로 이동한다. 미지원 팬 제어는 활성 슬라이더로 보여주지 않는다. 최소 속도 등 안전 정책은 장비에서 제공하는 값을 따른다.

연결 문제 해결은 `권한 / 장비 등록·인증 / 제어 경로 / 외부 통신`을 나눠 현재 부족한 단계만 안내한다. LAN·Wi-Fi Direct·BLE 선택 화면을 첫 사용의 필수 지식으로 만들지 않는다. 실제 네트워크 전환은 기존 영향 확인 후 요청한다.

앱 테마·알림 설정·앱 정보는 장비 연결과 독립이다. 앱 설정을 찾기 위해 연결 성공을 요구하지 않는다. 화면을 줄이려고 앱 설정과 장비의 전원 명령을 한 버튼 모음으로 섞지 않는다.

### 7.9 알림·오류·빈 화면

알림 목록은 공통 상단 종에서 연다. 장비 이름·발생 시각·문제·영향·이동 대상을 보여준다. 읽음/닫음 상태와 실제 장애 해결 상태는 별개다. 이전에 구현된 경고 닫기·지속 저장 정책을 무작정 제거하지 않는다.

하나의 문제를 상단 배너·작업 카드·센서 카드·Snackbar에서 동시에 반복 설명하지 않는다. 현재 동선을 막는 문제는 대표 배너 하나와 상세 진입점으로 정리한다. 안내를 닫더라도 영향을 받는 동작의 제한 이유는 남겨둔다. “안내를 닫음”을 “문제가 해결됨”으로 처리하지 않는다.

빈 화면은 제목·이유·가능한 주 행동 하나를 제공한다. 데이터 조회 실패를 `파일 없음`으로 표시하지 않는다. 로딩에는 완료 예상 시간을 발명하지 않고 현재 단계를 표시한다. 화면 새로고침 중에는 가능한 기존 내용을 유지한다.

문구 예시:

| 상황 | 사용자에게 보여줄 표현 |
|---|---|
| 제어 경로 끊김 | `장비와의 연결이 끊겼습니다. 마지막 상태를 표시합니다.` + `연결 확인` |
| 센서 데이터 지연 | `최근 센서 상태를 받지 못했습니다.` + 마지막 수신 시점 |
| 실행 응답 불명 | `실행 결과를 아직 확인하지 못했습니다.` + `현재 상태 확인` |
| 업로드 조건 미충족 | `이 연결에서는 서버 전송을 시작할 수 없습니다.` + 실제 가능한 연결 안내 |
| 실제 미지원 | `이 장비에서 제공하지 않는 기능입니다.` |
| 권한 거부 | 해당 권한이 필요한 이유 + 재요청 또는 앱 설정 이동 |

원인 설명과 시스템 오류 코드를 상세에 함께 보존한다. 모든 오류를 “다시 시도하세요”로 뭉개지 않는다.

## 8. 화면 상태와 조작 규칙

### 8.1 서로 다른 사실을 하나의 ‘정상’으로 합치지 않는다

| 축 | 구분할 상태 | 금지할 추론 |
|---|---|---|
| 장비 식별 | 미선택 / 등록됨 / 선택됨 | 등록됐으니 연결됨 |
| 제어 연결 | 미연결 / 확인 중 / 제한 연결 / 제어 가능 / 재연결 / 실패 | BLE만 연결됐으니 영상·파일 모두 가능 |
| 데이터 최신성 | 미수신 / 최신 / 지연 / 마지막 기록 | 저장된 수치가 있으니 지금도 정상 |
| 작업 | 미선택 / 준비 / 시작 요청 / 실행 / 중지 요청 / 정지 / 오류 / 확인 불가 | HTTP 응답 또는 버튼 탭이 곧 실제 실행 |
| 기능 가용성 | 지원 / 미지원 / 미설정 / 권한 필요 / 연결 필요 / 확인 불가 | 미지원과 일시적 실패가 같은 상태 |
| 외부 통신 | 휴대전화 인터넷 / 장비의 서버 접근 / RTK 중계 | 한 경로가 가능하니 다른 경로도 가능 |

이 표는 UI에서 구별할 개념이다. 각 화면에 별도 연결 상태 머신을 구현하라는 뜻이 아니다. 기존 Repository와 transport 정책을 단일 사실 출처로 삼고 표시용 모델로 변환한다.

### 8.2 명령의 수명

`사용자 의도 → 대상/권한/가용성 재확인 → 요청 중 → 장비 응답·현재 상태 확인 → 성공/실패/확인 불가`를 따른다. 회전·탭 복귀·프로세스 복원으로 시작·중지·업로드가 다시 실행되지 않게 한다.

서버가 멱등성을 보장하지 않으면 결과가 불명확한 명령을 자동 재전송하지 않는다. 먼저 상태를 조회하고 가능한 다음 행동을 제공한다. 기존 재연결·백오프·generation guard를 보존하며 별도의 타이머로 중복 복구를 만들지 않는다.

준비 상태 표시용 시간 초과와 네트워크 연결 엔진의 시간 초과를 혼동하지 않는다. UI의 스피너를 끝내기 위해 실제 연결을 임의 종료하거나, 진행률 애니메이션을 맞추려고 타이머로 연결 성공을 설정하지 않는다.

### 8.3 연결 끊김과 복구

일시 끊김은 현재 화면에서 안내하며 초안·스크롤·파일 선택을 유지한다. 현재 값은 마지막 기록임을 표시하고 상태가 불명확한 명령은 제한한다. 자동 복구가 성공해도 작업 시작 명령을 재발행하지 않는다.

재등록이 실제 필요한 인증 문제와 단순 네트워크 끊김을 구분한다. 복구를 위해 등록 정보를 먼저 삭제하거나 앱 저장소를 초기화하지 않는다. 다른 장비에서 온 늦은 응답이 현재 화면에 섞이지 않게 기존 식별자·세대 구분을 확인한다.

### 8.4 저장과 복원

장비 ID, 작업 ID, 선택 폴더, 필터, 스크롤 위치, 작은 비민감 UI 상태만 저장·복원한다. 대용량 이미지·파일 목록·원시 로그·인증 정보는 navigation arguments나 `rememberSaveable`에 넣지 않는다. 비밀값은 기존의 적절한 저장 계층을 유지한다. [A5]

프로세스 복원 시 `Connected`, `RUNNING`, `RTK FIX`를 저장값만으로 현재 상태로 사용하지 않는다. 재확인 동안 `마지막 확인 상태`와 `현재 확인 중`을 구분한다. 작업 설정 초안은 원격 적용값과 구별하고 적용 성공 여부를 표시한다.

## 9. 코드 구조와 기능 재연결

### 9.1 리빌딩 경계

```text
실제 장비 / 기존 API
       ↓
기존 Repository · transport · 서비스
       ↓
기존 또는 정리된 ViewModel / 표시 상태 변환
       ↓
새 AppShell · 새 화면 · 공통 컴포넌트

Preview/debug fixtures → 같은 새 화면 (디자인 검증 전용)
```

새 UI가 기존 ViewModel에 맞지 않으면 얇은 표시용 변환 계층을 둔다. 그러나 각 버튼마다 UseCase/Repository/Manager를 새로 생성하는 대형 구조 전환은 하지 않는다. 기존 거대한 화면 파일은 책임에 따라 분리해도 된다.

`JetsonApp.kt`에 모든 새 UI와 모든 비즈니스 판단을 추가하지 않는다. 내비게이션과 화면 연결은 shell/route 책임으로, 표시 상태 변환은 ViewModel 또는 작은 순수 함수로, 실제 명령과 연결 상태 관리는 기존 하위 계층으로 나눈다. Compose의 상태 상향과 lifecycle-aware 수집을 적용한다. [A8]

### 9.2 수정 지점 지도

아래에서 경로는 `app/src/main/java/com/example/jetsoncontroller/` 기준이다. 새 파일명은 제안이며 현재 트리에서 먼저 확인한다.

| `ui/connection/*`, `ui/devices/*`, `ui/pairing/*`, `ui/onboarding/*` | 장비 등록·선택·연결과 필요한 권한 흐름을 새 UI에 연결 |

| `data/transport/TransportPolicy.kt` 및 연결 계층 | 새 UI의 가용성 판단에 재사용. 시각 변경만으로 정책 수정 금지 |

### 9.3 바인딩 계약표를 실제 코드로 채운다

| 새 UI 정보/행동 | 우선 확인할 실제 출처 | 주의 |
|---|---|---|
| 선택 장비·제어 가능 여부 | 등록 장비·선택 장비 상태, `TransportState`, capabilities | `isOnline` 하나로 모든 기능을 판단하지 않음 |
| 현재 작업·실행 제어 | `ManagedPipeline`, `PipelineUiState`, 기존 control 콜백 | 표시 ID와 실제 명령 대상이 일치해야 함 |
| 홈 건강·지연 상태 | `DashboardUiState`, 기존 freshness/health 판정 | 정상 기준·경고 dismiss 정책을 중복 구현하지 않음 |
| 영상 | `CameraPreviewUiState`, sensor telemetry | `frameRevision`·수신 시각·센서 활성 구분 |
| 위치·센서 | 기존 GNSS·IMU·sensor presentation과 위치 ViewModel | 장비 위치/휴대전화 위치와 최신성 구분 |
| 결과 이동 | 실제 output root/path와 저장소 상태 | 파일 이름·시간만으로 결과를 추정하지 않음 |
| 서버 전송 | 기존 upload state·capabilities·transport policy | LAN 제한과 서버별 조건 유지 |
| 앱/장비 설정 | 기존 설정 저장소와 서비스 명령 | UI 표시값과 실제 적용값 구분 |

계약표의 각 항목에는 `LIVE_BOUND / PREVIEW_ONLY / UNSUPPORTED / INTENTIONALLY_REMOVED / BLOCKED`를 부여한다. 사용자에게 보여주는 제품 화면에서 `PREVIEW_ONLY`가 실제 기능처럼 남아 있으면 완료가 아니다.

### 9.4 디자인 선행과 샘플 데이터의 경계

실제 장치 없이도 모든 상태를 검토할 수 있도록 Preview와 debug 전용 디자인 갤러리를 만든다. 새 production Composable을 같은 방식으로 사용하고 데이터만 교체한다. 갤러리의 상태 토글은 장비를 제어하지 않는다.

샘플 데이터·가짜 저장소·상태 토글 진입점은 `src/debug`, 테스트 source set 또는 동등한 격리 구조에 둔다. 런타임 갤러리에는 `디자인 검증용 예시`를 표시한다. release 화면에서 `데이터 없음 → 정상 샘플 표시` 같은 fallback을 사용하지 않는다. 최종에는 release에서 갤러리 접근 경로·fake binding이 없는지 확인한다.

디자인을 위해 Web 프로토타입을 보조로 만들 수는 있지만 그것만 제출하고 끝내지 않는다. 제품 산출물은 네이티브 앱의 실제 화면이다. 원본이 React/HTML이어도 필요한 의도만 Compose로 옮긴다.

## 10. 실행 순서와 단계별 종료 조건

### 단계 0 — 확인과 범위 확정

현재 코드·사용자 변경·기능 지도·참고 artifact 접근 상태를 기록한다. 디자인 방향은 §5~§7의 기본안으로 시작한다. 실기기 접근 여부는 기록하되 UI 설계의 필수 전제는 아니다.

**통과:** 변경 경계와 실제 상태 출처를 설명할 수 있고, 기존 데이터를 건드리지 않을 작업 경로가 확보됨.

### 단계 1 — 디자인 토큰과 새 화면 뼈대

공통 테마·컴포넌트·AppShell을 만든다. 현장, 작업 상세, 데이터, 장비를 같은 완성도로 구현하고 화면 상태 Preview를 만든다. 실제 API를 모두 붙일 때까지 화면 설계를 미루지 않는다.

**통과:** 4개 주 탭의 정상/빈 상태를 실제 렌더링해서 검토했고, 새 스타일·헤더·하단 메뉴·insets가 일관됨. 이전 화면을 새 배경으로 감싼 것에 그치지 않음.

### 단계 2 — 사용자 흐름과 상태 디자인 완성

등록→장비 선택→준비 확인→작업→현장 집중→결과→전송 흐름을 연결한다. 연결 끊김·권한 거절·명령 불명·오래된 영상·장비 미지원도 디자인한다. §4의 기능 제거·이동 결정을 반영한다.

**통과:** debug 갤러리/Preview에서 성공 화면뿐 아니라 실패와 제한 상태도 탐색 가능. 실제 명령이 없는 예시 흐름임을 구분할 수 있음.

### 단계 3 — 기존 기능 재연결

장비 선택·연결 → 작업 → 센서·영상/위치 → 데이터·전송 → 설정·알림 순으로 실제 상태와 콜백을 붙인다. 각 연결 후 관련 자동 테스트를 수행한다. 실데이터 구조가 설계와 맞지 않으면 §13에 따라 UI를 조정한다.

**통과:** 핵심 바인딩이 실제 계층에 연결되고, 장비 ID·권한·capabilities·진행 상태가 올바르게 적용됨. 백엔드에 없는 기능은 거짓 버튼 대신 제거/대안 처리됨.

### 단계 4 — 구형 UI 정리와 회귀 검사

신규 경로로 이전이 끝난 구형 화면·중복 컴포넌트·죽은 메뉴를 제거한다. 사용 중 route·알림 목적지·저장 키를 검색하고 새 목적지로 이어지는지 테스트한다. 연결 안정성 수정은 별도 회귀 검사로 보존한다.

**통과:** 동일 기능에 서로 다른 스타일의 두 화면이 남지 않으며, 구형 화면 제거로 핵심 기능이나 알림 이동이 끊기지 않음.

### 단계 5 — 실기기·접근성·성능 검증

§11의 검증을 수행한다. 동일 장비·동일 조건의 전후 화면을 비교하고, 디자인으로 생긴 스크롤/프레임 지연/자원 누수를 점검한다. 장치 접근이 막힌 항목은 `BLOCKED`로 남긴다.

**통과:** 실행한 검증과 미실행 검증이 분리되어 있으며, 접근 가능한 범위의 결함을 수정함. 실기 미검증 상태를 통합 완료라고 선언하지 않음.

### 단계 6 — 납품과 정리

§12의 결과·디자인 규칙·검증 증거를 남긴다. 전체 완료 조건을 충족했을 때만 §15의 지침 파일 삭제를 수행한다.

작업이 중단되면 마지막 완료 단계, 남은 파일, 실패한 테스트, 다음 작업을 결과 보고서에 남긴다. 단순히 “계속 진행하면 됩니다”라고 끝내지 않는다. 독립적으로 진행 가능한 항목이 있으면 계속한다.

## 11. 검증 기준

### 11.1 빌드·자동 검사

저장소의 현재 wrapper·버전 카탈로그·CI를 먼저 읽고 도구 체인을 맞춘다. Kotlin/Compose/SDK/Gradle의 일괄 최신화는 디자인 작업의 전제 조건이 아니다. 기존 빌드 오류를 새 코드 회귀와 구분한다. [R2], [R13]

아래는 Unix 계열 기본 명령이며, Windows 네이티브에서는 같은 작업에 `gradlew.bat`를 사용한다.

```bash
./gradlew :app:assembleDebug :app:lintDebug :app:testDebugUnitTest --console=plain
```

연결된 테스트 대상 또는 에뮬레이터가 확보되고 실행 영향이 통제된 경우:

```bash
./gradlew :app:connectedDebugAndroidTest --console=plain
```

여러 기기가 있으면 현재 도구 체인에서 지원하는 방식으로 대상을 명시적으로 선택한다. Gradle/ADB가 임의 기기를 선택하게 하지 않는다. 명령 종료 코드뿐 아니라 XML 결과의 실행 수·실패·skip을 확인한다. 환경 미비로 실행하지 못한 테스트를 통과로 기록하지 않는다.

백엔드를 수정했다면 기존 백엔드 회귀 검사와 영향받는 API 검사를 수행한다. UI 리빌딩을 위해 기존 lint 경고를 일괄 끄거나 테스트를 삭제하지 않는다. 의도적으로 변경한 화면 문구·탭 순서는 새 계약으로 테스트를 고치고 변경 이유를 남긴다.

### 11.2 필수 자동 테스트 계약

| 검증 | 통과 조건 |
|---|---|
| 4탭과 상세 이동 | 탭 재선택 중복 없음, 상세 복귀 위치 유지, 알림 목적지 유효 |
| 장비 전환 | A의 초안·파일·늦은 응답이 B에 나타나지 않음 |
| 연결/가용성 | BLE·LAN·Wi-Fi Direct·오프라인·미지원의 동작 제한이 실제 정책과 일치 |
| 준비 확인 | 선택 작업의 필수 조건만 사용, 실행으로 기동되는 센서 때문에 시작을 막지 않음 |
| 명령 | 중복 탭·회전·화면 복귀로 재전송되지 않음, 응답 불명 상태 처리 |
| 영상 최신성 | 첫 프레임 없음/같은 revision/오류 후 이전 프레임/새 프레임을 구별 |
| 센서·지도 | 최신성·위치 출처·RTK 상태 구분, 모바일 위치를 장비 위치로 위장하지 않음 |
| 데이터·전송 | 출처·선택 복원·LAN 시작 제한·진행률의 실제 근거·실패 이력 유지 |
| 경고 닫기 | 알림 dismiss와 실제 장애 상태 구분, 장비별 저장 정책 보존 |
| 안전 액션 | 중지·재시작·등록 해제·전원의 확인 대상과 취소 동작 검증 |
| 복원 | 프로세스 재생성 후 초안 복원, 현재 연결·실행은 재확인 |
| release 분리 | 디자인 갤러리·fake binding·자동 샘플 성공 상태가 제품 경로에 없음 |

기존의 `CoreWorkflowScreenTest`, 연결 정책·상태·내비게이션·센서·업로드 관련 테스트 중 현재 트리에 있는 것을 먼저 찾는다. 없는 테스트 이름을 존재한다고 가정하지 않는다. 새 테스트는 표시 상태의 순수 함수와 화면 상호작용을 나눠 추가한다.

### 11.3 시각·접근성 검사

대표 폭은 360dp·412dp·600dp와 실제 휴대전화 폭으로 확인한다. 기본/1.3배/2.0배 글꼴, 밝은/어두운 테마, 세로/가로, 제스처/3버튼 내비게이션, 키보드 표시, 긴 한글 이름을 검사한다. 이는 설계 검증 조합이며 제품의 지원 기기 범위를 새로 선언하는 것이 아니다.

한 폭에 맞추기 위해 텍스트를 자동 축소하거나 고정 높이에 잘라 넣지 않는다. 일반 휴대전화는 한 열을 기본으로 하고, 넓은 창은 목록·상세 또는 주 콘텐츠·보조 패널로 전환한다. 기기 모델명이 아니라 사용 가능한 창 크기를 기준으로 배치한다. [A9]

Material 3의 자체 insets와 `Scaffold`의 padding을 함께 고려해 한 책임 지점에서 적용한다. 상태바·하단바 높이를 하드코딩하지 않는다. 키보드 위 액션과 목록 끝 항목이 가려지지 않아야 한다. [A7]

TalkBack의 탐색 순서, 버튼 라벨, 선택 상태, heading, 상태 메시지를 검사한다. 배지·장비명·행 전체를 무조건 합쳐 세부 행동을 잃게 하지 않는다. 색상·아이콘·제스처만으로 중요한 동작을 설명하지 않는다. 초당 바뀌는 수치·영상 상태를 매번 음성 공지하지 않는다. [A2], [A10]

**시각 합격 체크:** 좌우 여백, 텍스트 크기, 버튼 위계, 상태색, 모서리, 아이콘, 헤더·하단 메뉴, 빈 화면·오류 화면이 일관된가? 주요 사용자 행동보다 정상 지표·장식·위험 버튼이 먼저 보이지 않는가? 코드만 보고 합격시키지 말고 실제 렌더링 결과를 확인한다.

### 11.4 실제 장치 시나리오

| 상황 | 확인할 것 |
|---|---|
| 첫 설치 또는 등록 없음 | 필요한 권한만 요청, QR와 대안, 실패 후 재진입 |
| 등록 장비 재접속 | 저장 상태와 현재 상태 구분, 준비→제어 가능 표시 |
| LAN / Wi-Fi Direct / BLE | 각 모드의 실제 기능 범위, 연결 방식 설명과 복구 |
| 진행 중 작업 있는 앱 재진입 | 실제 작업 동기화, 자동 시작/중지 없음 |
| 작업 시작·중지 | 대상 장비·작업 확인, 상태 응답, 중복 명령 없음 |
| 영상 확인과 화면 이탈 | 새 프레임·지연 구분, 구독/메모리 누수 없음, 장비 수집은 유지 |
| GNSS·RTK·모바일 중계 | 실제 수신 상태·출처·경로 설명이 장치와 일치 |
| 결과 조회·전송 | 실제 output 경로, 서버 대상, 연결 제한·진행 상태 |
| 네트워크 일시 끊김·복구 | 초안/선택 유지, 현재값과 마지막값 구분 |
| 화면 회전·백그라운드·복귀 | UI 복원, 서비스 유지 정책, 중복 수집기 없음 |
| 장비 교체 | 지연 응답·기존 캐시·이력·명령 대상 분리 |
| 권한 변경·미지원 장치 | 무한 로딩 없이 이유와 대안 표시 |

끊김·강제 종료·재부팅 시험은 실제 수집·업로드·RTK 중계를 방해할 수 있다. 승인된 테스트 장비와 상황에서만 수행한다. 그 외에는 상태 주입 테스트로 검증하고 실기 항목을 남긴다. UI 테스트를 위해 장비 네트워크나 전원을 무단 변경하지 않는다.

### 11.5 경량성·성능 예산

같은 변형·빌드 설정·장비·데이터·온도 조건에서 비교한다. 시작 시간, 스크롤 프레임, 메모리, APK 크기, 영상/지도 전환 후 자원 회수를 확인한다. debug 성능을 최적화된 release의 성능처럼 설명하지 않는다.

의미 없는 UI 변화로 새 네트워크 폴링이 생기거나 영상이 중복 요청되면 실패다. 가능하면 상호작용 즉시 눌림/요청 중 피드백을 제공하되 장비 응답까지 즉시 성공 처리하지 않는다.

같은 조건에서 시작 시간·대표 화면 메모리가 반복 측정상 10% 넘게 나빠지면 원인 조사와 수정 여부를 기록하는 내부 경고선으로 사용한다. 이 숫자는 보장 성능이나 업계 기준이 아니다. 측정 자체가 불가능하면 `NOT_MEASURED`로 표시한다. 스크롤·영상의 체감 성능 저하는 수치 경고선 미만이어도 수정 대상이다.

## 12. 산출물과 완료 판정

### 12.1 남겨야 할 결과

1. 실행 가능한 새 Compose UI와 실제 기능 바인딩, 필요한 마이그레이션 및 테스트.
2. `docs/design/DESIGN_SYSTEM.md`: 최종 토큰, 컴포넌트 규칙, 내비게이션, 상태·문구 규칙. 기존 동등 문서가 있으면 중복 생성하지 말고 갱신.
3. `docs/design/DESIGN_REBUILD_RESULT.md`: 기준/최종 HEAD, 변경·제거·추가, 원본 대조 상태, 바인딩표, 테스트·실기 결과, 미완료 항목, 롤백 방법.
4. 실제 전후 스크린샷과 상태별 검증 자료. 큰 바이너리는 기존 산출물 보관 방식에 맞추고 민감 정보는 제거.

문서 파일 수를 늘리는 것이 목표가 아니다. 상태표와 결정 기록은 결과 보고서에 모으고, 디자인 갤러리는 유지보수에 유용한 debug 도구로 남길 수 있다.

### 12.2 완료를 세 축으로 나눈다

| 축 | 가능한 상태 | 판정 의미 |
|---|---|---|
| 디자인 구현 | `DONE / PARTIAL` | 새 화면·상태·상호작용이 실제 렌더링되고 일관되게 구현되었는가 |
| 기능 통합·검증 | `VERIFIED / PARTIAL / BLOCKED` | 실제 기능 바인딩과 필수 자동·실기 검증이 끝났는가 |
| 참고 디자인 대조 | `VERIFIED / PARTIAL / REFERENCE_UNVERIFIED` | Claude 원본을 확인했고 채택·변형 내용을 대조했는가 |

디자인만 완성되면 `디자인 DONE / 통합 BLOCKED`처럼 보고한다. 원본 접근이 막혀도 독립 재설계의 완성 여부는 별도로 보고할 수 있다. 그러나 `REFERENCE_UNVERIFIED`인데 “요청한 참고 디자인까지 반영한 전체 작업 완료”라고 쓰지 않는다.

### 12.3 전체 완료 체크

- [ ] 새 정보 구조와 전반적인 화면 변화가 구현되었다. 색·모서리 변경만으로 끝나지 않았다.
- [ ] 유지/이동/추가/삭제한 항목과 사용자 가치가 기록되었다.
- [ ] 핵심 기능 바인딩이 완료됐고, 화면에 존재하지만 동작하지 않는 필수 액션이 없다.
- [ ] 장비·작업·센서·프레임·위치의 현재/과거/미확인 상태가 구분된다.
- [ ] 기존 사용자 데이터·등록·인증·초안·안전 정책이 보존되었다.
- [ ] 연결 방식별 기능 범위와 전송 제한이 실제 구현과 일치한다.
- [ ] 접근성·화면 배율·테마·시스템 바와 키보드 검사를 수행했다.
- [ ] 자동 테스트와 필수 실기 검증이 통과했다. 미실행을 통과로 세지 않았다.
- [ ] release 제품 경로에 데모 상태·가짜 성공·디자인 갤러리 진입점이 없다.
- [ ] 구형 UI의 중복·죽은 경로가 정리됐고 필요한 기능·알림 경로는 이어진다.
- [ ] 참고 디자인 대조가 완료됐거나, 사용자가 원본 미대조의 독립안으로 완료 범위를 명시적으로 변경했다.
- [ ] 최종 규칙과 결과·증거·복구 방법이 별도 산출물에 보존되었다.

전체 완료 전에도 검증된 디자인·구현 결과는 납품한다. 다만 막힌 항목을 숨기거나 이 MD를 성급히 삭제하지 않는다.

## 13. 문서와 실제 코드·장치가 다를 때의 자율 조정

문서는 절대 명세가 아니다. 더 적절한 해결책이 있으면 적용하되, 다음 기준을 따른다.

| 불일치 | 선택할 행동 |
|---|---|
| 원본 artifact가 다른 좋은 시각 방향을 제시 | 색·타이포·형태·레이아웃의 의도를 비교해 채택. 미지원 기능·접근성 결함까지 복제하지 않음 |
| 기존 코드가 이미 제안보다 좋은 흐름을 갖춤 | 그 동작을 재사용하고 새 디자인 시스템으로 정리. 중복 재작성하지 않음 |
| 새 화면에 필요한 데이터가 API에 없음 | 기존 데이터로 의미를 바꾸거나 항목 제거·확인 불가 표시. 가짜 데이터나 추정값 금지 |
| 준비 확인의 센서 판정이 실행을 영구 차단 | 실행 전 필수 조건과 실행 후 활성 조건을 분리. 실제 작업 생명주기에 맞춤 |
| 전송/재시도/취소 계약이 설계와 다름 | 실제 지원 계약에 UI를 맞춤. 범위를 넘는 새 서버 기능은 별도 항목으로 기록 |
| 좁은 화면·큰 글꼴에서 4탭 기본안이 불편 | 줄바꿈·유연한 높이·상세 분리 등으로 조정. 글씨 축소로 감추지 않음 |
| 장치 성능 때문에 복합 화면이 무거움 | 영상/지도를 탭으로 분리, 부가 수치 갱신 축소. 실제 수집·기록 주기는 임의 변경하지 않음 |
| 센서 탭 제거로 실제 주 작업이 어려워짐 | 진입점을 현장에 확대하거나 탭 구성을 재조정하고 근거 기록 |
| 사용 가치가 없는 실제 기능을 발견 | 사용자 데이터·핵심 가치·대체 경로를 검토한 뒤 제거 가능. 제거 이유를 기능표에 기록 |
| 작업 트리와 충돌하거나 실기 접근이 없음 | 독립적인 화면·테스트 작업은 계속, 영향을 받는 통합은 BLOCKED로 구분 |

결정 기록은 `문서 기본안 → 관찰한 사실 → 채택한 변경 → 영향 → 검증`으로 간단히 남긴다. 사소한 디자인 선택을 사용자에게 반복 질문하지 않는다. 범위가 커졌다는 이유로 분석만 제출하지 않는다. 동시에 승인 없는 배포·원격 전원/네트워크 변경·데이터 삭제는 하지 않는다.

## 15. 작업 완료 후 이 MD 파일만 제거한다 — 최종 필수 작업

**전체 작업과 필수 검증을 완료하면, 디자인 규칙·추가/제거 결정·기능 연결·검증 결과를 별도 산출물에 남긴 뒤, 작업 지침으로 읽은 이 MD 파일을 제거한다.**

작업 시작 시 기록한 실제 경로의 `JETSONCONTROLLER_DESIGN_REBUILD_AI_AGENT.md` 또는 사용자가 같은 지시서에 지정한 실제 파일만 대상으로 한다. 파일이 추적 중이면 해당 파일의 삭제 변경을 남기고, 추적되지 않은 파일이면 그 파일만 제거한다. 이름 패턴으로 다른 MD를 일괄 삭제하지 않는다.

`AGENTS.md`, 기존 프로젝트 문서, 이전 지침 파일, 최종 디자인 시스템, 결과 보고서, 테스트, 검증 증거는 이 정리 지시의 삭제 대상이 아니다. 과거 지침과의 우선순위는 결과 보고서에 남기고 다른 문서를 임의로 지우지 않는다.

필수 기능 재연결·실기 검증 또는 원본 대조가 남아 전체 완료 조건을 충족하지 못하면, **이 MD를 유지하고 완료된 범위와 차단 사유를 명확하게 보고한다.** 원본 미대조의 독립안으로 사용자가 완료 범위를 명시적으로 변경한 경우에는 변경된 범위의 충족 여부로 판단한다. 삭제 자체를 완료의 근거로 삼지 않는다.
