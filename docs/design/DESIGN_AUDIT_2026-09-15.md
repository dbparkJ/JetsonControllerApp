# 디자인 감사 — 기존 UI와 전달받은 브리프

2026-09-15 · 기준 커밋 `0081445`

의뢰가 "첨부 문서를 전적으로 믿지 말고 비관적으로 보라"였으므로, 이 문서는
**기존 화면의 문제**와 **브리프 자체의 문제**를 나눠서 적습니다.

검토 범위: `main` 의 소스·문서·머지 기록. **실제 APK를 설치해 실기에서 조작하거나
화면을 캡처하지 않았습니다.** 아래 A항목은 코드에서 직접 확인한 사실이고, B항목은
추론입니다. 구분해서 읽어 주세요.

---

## A. 코드에서 확인한 결함

### A1. 상태색이 존재하지 않았다 — 심각

`ui/theme/Color.kt` 에서:

```kotlin
success = Color(0xFF525862)   // CobaltLight
muted   = Color(0xFF525862)   // 같은 값
successBg = Color(0xFFEBEEF1)
subtle    = Color(0xFFEBEEF1) // 같은 값
```

`success` 와 `muted` 가 바이트 단위로 동일했습니다. 다크에서도
`success = #B5BBC5` 로 같은 문제가 반복됩니다. 결과적으로:

- "저장 확인됨" 배지와 비활성 보조 라벨이 구별되지 않습니다.
- `StatusBadge(label, SUCCESS)` 와 `StatusBadge(label, INFO)` 중 SUCCESS 쪽이
  **더 눈에 덜 띕니다** (INFO는 파란 계열이라 채도가 있음).
- 브리프가 최우선으로 막으라고 한 오독 — "연결됐으니 저장도 됐다" — 을
  팔레트가 직접 조장합니다.

이건 취향 문제가 아니라 시스템 결함입니다. 레이아웃을 아무리 고쳐도 해결되지 않습니다.

### A2. '모른다'를 표현할 토큰이 없었다 — 심각

`StatusTone` 은 `INFO / SUCCESS / WARNING / ERROR` 네 값뿐이었습니다. 그런데
브리프 11.1의 상태표는 17개 행 중 **7개가 '미확인·처리 중' 계열**입니다.

기존 코드가 이걸 어떻게 처리했는지 보면:

- `DashboardHealthLevel.UNKNOWN` → `StatusTone.INFO` (파란 안내색)
- `checkLabel("STALE")` → `"확인 필요"` — 실패와 같은 문구로 번역됨
- `preflight == null` → `INFO`, `!ready` → `WARNING` — 둘 다 '모른다'가 아님

`STALE`(값이 오래됨)과 `FAILED`(실패)를 같은 "확인 필요"로 번역한 건 실제 버그에
가깝습니다. 전자는 재조회가 필요하고 후자는 수리가 필요합니다.

### A3. 타이포 스케일에 중간 단계가 없었다

`bodyLarge` 와 `bodyMedium` 이 둘 다 `16.sp / 24.sp`. 본문과 강조 본문이 같은
값이라 화면이 쓸 수 있는 단계가 사실상 하나 줄어 있었습니다.

### A4. 숫자가 비례 폰트였다

용량·시간·파일 수·퍼센트가 모두 비례 숫자로 렌더링됩니다. `19%` → `20%` 에서
글리프 폭이 달라 행이 흔들립니다. 브리프 12.4가 "갱신 때 레이아웃이 심하게
흔들리지 않게"를 요구하는데 토큰 레벨에서 대응이 없었습니다.

### A5. 간격 토큰이 중복 정의돼 있었다

`AppSpacing.large = 16.dp` 와 `AppSpacing.screen = 20.dp` 가 의미상 겹치고,
실제로 화면마다 `16.dp` / `20.dp` / `14.dp` 가 하드코딩돼 섞여 있습니다
(`DashboardScreen` 의 `14.dp`, `MetricCard` 의 `14.dp`, `PipelineScreens` 등).
"같은 토큰을 쓰는데 다르게 보이는" 상태였습니다.

### A6. 모든 것이 카드였다

`SectionSurface(color)` 가 호출자마다 다른 틴트를 받도록 설계돼 있어서
(`sectionSoft`, `sectionRaised`, `dangerBg`, `hero` …) 한 화면에 색이 다른
블록이 5~6개 쌓입니다. 브리프 12.4의 "모든 항목을 카드로 감싸지 않음"과
정반대이고, 진짜 경고가 장식적 색 블록에 묻힙니다.

### A7. 라운드가 과했다

`medium 20dp / large 24dp / extraLarge 28dp`. 소비자 생활 앱의 값입니다.
브리프 1.4가 피하라고 한 바로 그 인상입니다.

### A8. deprecated 시스템 바 API

`Theme.kt` 가 `window.statusBarColor` / `navigationBarColor` 를 `@Suppress` 로
설정합니다. `targetSdk = 37` 에서는 무시되는 no-op이므로 실제로는 아무 일도 하지
않는 코드였습니다. 제거하고 인셋 기반 처리만 남겼습니다.

### A9. 홈의 정보 우선순위가 뒤집혀 있었다

`GeoDeviceSummary` 는 CPU / GPU / 온도를 `titleLarge` 로 카드 하단에 배치합니다.
"어느 장치인가"를 답해야 하는 카드에서 **개발자 텔레메트리가 가장 큰 활자**를
차지하고 있었습니다. 브리프 1.3이 정확히 이걸 지적합니다.

또 홈에 상시 안내 배너가 하나 고정돼 있었습니다:

> "작업 시작에서 프로젝트·조사 구간·수집 정책을 선택하고 장비의 필수 점검 근거를
> 확인하세요."

상태와 무관하게 항상 같은 문장이 뜨는 사용 설명서입니다. 이런 건 두 번째 사용부터
읽히지 않고, 진짜 메시지가 떴을 때 같이 무시당합니다.

### A10. 현장 직원에게 바이트 단위 입력을 요구했다

`SurveyRunScreen` 의 정책 패널은 "시작 전 최소 여유 공간 (bytes)", "최소 파일 수",
"최소 bytes", "예상 파일 패턴" 을 **시작 버튼에 도달하기 전 경로에** 놓습니다.
브리프 10장이 "관리자가 준비한 정책을 이해하고 확인하는 흐름을 우선"이라고
적었는데 구현은 반대입니다. 안전 정책을 매번 넘겨야 하는 폼으로 만들면 사람은
그 폼을 넘기는 법을 배웁니다.

### A11. 점검 결과가 문단이었다

```kotlin
Text("시간 ${checkLabel(...)} · 저장 공간 ${checkLabel(...)}")
```

시간과 저장 공간이 한 줄에 이어 붙습니다. 센서는 그 아래 `bodySmall` 로 나열되고
문제는 다시 그 아래. 센서 하나가 실패했을 때 문장을 읽어야 알 수 있습니다.

### A12. 탭 이름이 시스템 용어였다

`홈 / 작업 / 데이터 / 설정` 의 "작업"은 코드의 `pipeline`/`task` 에서 온 말입니다.
제품의 데이터 모델은 프로젝트 → 구간 → **실행**이고 사용자의 업무는 **조사**입니다.

## B. 실기 확인이 필요한 추론

코드만으로는 단정할 수 없어 실제 단말 확인이 필요한 항목입니다.

- **B1.** 시스템 글꼴 200%에서 `DeviceContextHeader` 의 장치명 + 제목 + 연결
  라벨이 3줄로 늘어날 때 하단 콘텐츠를 얼마나 밀어내는지.
- **B2.** `SwipeToDismissBox` 로 감싼 홈 상태 카드가 `LazyColumn` 스크롤과
  제스처 충돌을 일으키는지. 브리프는 제스처만으로 필수 동작을 수행하게 하지 말라고
  하는데, 이 카드는 닫기 버튼이 병행되므로 규칙 위반은 아닙니다.
- **B3.** 야외 직사광선에서 새 상태색의 구별. 계산상 대비는 통과하지만 실제
  휘도 환경은 계산으로 대체되지 않습니다.
- **B4.** 삼성 3버튼 내비게이션에서 `GeoBottomActionBar` + `NavigationBar` 가
  겹쳐 쌓였을 때 총 높이. `DataHubScreen` 은 두 개가 세로로 붙습니다.

## C. 브리프 자체의 문제

전달받은 `JetsonControllerApp_DESIGNER_BRIEF_PRD_KO.md` 는 대체로 정확하고
솔직합니다(특히 "확정 결함 목록이 아니다"라는 자기 제한). 다만 다음은 그대로
따르면 안 됩니다.

### C1. 산출물 목록이 일정과 맞지 않는다

14장이 요구하는 것: 현행 화면 목록, 새 정보 구조, 핵심 흐름 와이어프레임,
시각 방향 2~3안, **전체 화면군 고해상도**, 인터랙션 프로토타입, 디자인 시스템,
개발 전달 명세, 디자인 QA 기록.

16장의 일정: 10월 중순 시연 준비 마감, 11월 첫 주 엑스포.

10장 표에 화면군만 14개(S01~S14)이고 각각 상태 변형이 3~5개입니다. 전체
고해상도 + 프로토타입 + 라이트/다크 + 폰/태블릿이면 **최소 200장 이상**입니다.
한 달에 안 됩니다. **시연 경로 한 줄(연결 → 점검 → 수집 → 결과)만 완성도를
올리고 나머지는 컴포넌트 명세로 대체**하는 게 현실적입니다.

### C2. 시각 방향 2~3안 비교를 먼저 하라는 요구가 이번 상황과 안 맞는다

12.3이 "같은 대표 화면으로 2~3개 방향 비교"를 요구합니다. 일반적으로는 맞는
절차지만, 이 프로젝트에는 이미 **U03이라는 확정된 제약**이 있습니다: 과채도 지양,
초록 중심 회귀 금지, 라이트·다크 모두 구분 가능. 여기에 승인된 기업 로고까지
있으면 실질적 선택지는 하나입니다. 색 시안 3개를 만들어 비교하는 건 형식이고,
**실제로 비교할 가치가 있는 축은 정보 밀도와 탐색 방식**입니다.

이번 작업은 그래서 방향 비교를 건너뛰고 한 방향을 구현했습니다. 이건 절차를
생략한 것이므로 명시해 둡니다 — 리뷰에서 방향 자체를 되돌릴 수 있습니다.

### C3. 브리프가 자기 근거의 한계를 정확히 적었지만, 그래서 신뢰도가 낮은 항목이 있다

R08 `UI_UX_DESIGN_SYSTEM.md` 와 R09 `GEO_FIELD_FEATURES.md` 는 2026-09-12 전후
문서입니다. 브리프도 "R09의 '서버 보관함은 Jetson 중계만 가능'을 최신 제한으로
적용하면 안 된다"고 적었습니다. 그런데 4장의 "재설계가 해결해야 하는 문제" 표는
상당 부분 이 오래된 문서들의 서술을 전제로 쓰였습니다. **4장 표는 검증 과제
목록으로만 쓰고, 확정 결함으로 다루지 마세요.**

### C4. 성공 기준에 수치가 없다

7.4가 "작업 완료 시간·성공률의 수치 목표는 현재 앱의 기초 측정 후 정한다"고
적었습니다. 정직한 태도지만, 그 결과 **이번 디자인이 성공했는지 판정할 방법이
아직 없습니다.** 최소한 다음 두 개는 시연 전에 측정해야 합니다.

1. 준비된 장치에서 연결 → 저장 확인까지 진행자 개입 없이 완료하는 비율.
2. "연결됨" 화면을 보여주고 "지금 데이터가 저장되고 있나요?"라고 물었을 때
   정답률.

2번이 이 개편의 핵심 가설이고, 측정이 5분이면 됩니다.

### C5. "필수 센서를 디자인 단계에서 임의로 선택 항목으로 낮추지 않습니다"의 반대쪽이 비어 있다

6.3이 이렇게 적었는데, 그럼 **현재 코드에 들어 있는 시험용 임시 값이 운영 기준이
아니라는 것을 화면에서 어떻게 표시할지**는 정해지지 않았습니다. 지금 구현은
정책 버전(`v3`)을 배지로 보여주지만, 그 버전이 "관리자가 승인한 운영 정책"인지
"누군가 테스트하다 저장한 값"인지 구별할 수 없습니다. **정책에 승인 주체와
승인 시각 필드가 필요합니다.** 이건 디자인이 아니라 데이터 계약 요청입니다.

### C6. Wi-Fi Direct 전제와 LAN 전용 업로드가 정면 충돌한다

2.1: 기본 현장 연결은 Wi-Fi Direct 전제.
5.2: `TransportPolicy.kt` 는 LAN에서만 업로드 시작 허용.

즉 **기본 현장 연결에서는 전송을 시작할 수 없습니다.** 브리프는 이걸 "제한 사유와
LAN 연결 안내가 필요"라는 UI 과제로만 다루는데, 이건 UI로 덮을 문제가 아니라
운영 시나리오의 구멍입니다. 현장에서 수집을 마친 직원이 전송하려면 매번 LAN
환경으로 이동해야 한다는 뜻인지, 아니면 Wi-Fi Direct 업로드를 지원할 계획인지
**PM·백엔드 결정이 먼저**입니다. 디자인은 현재 제한을 정직하게 표시하도록만
했습니다.

## D. 이번 작업에서 하지 않은 것

- 컴파일·실행·실기 검증 (환경에서 Android SDK 접근 불가)
- 시각 방향 2~3안 비교 (C2 참조)
- S01/S02/S07/S08/S09/S10/S11/S12/S13 화면의 개별 재설계 — 토큰과 컴포넌트
  교체로 자동 반영된 수준
- 태블릿 목록·상세 2단 레이아웃 (브레이크포인트 토큰만 준비)
- IA 재편 (탭 이름 외에는 기존 라우트 유지)
- 사용자 관찰·인터뷰
