# 자전거 도로 현장 조사 업무 흐름

기준일: 2026-09-14
관련 제품 결정: [PRODUCT_DEFINITION_KO.md](PRODUCT_DEFINITION_KO.md)

## 1. 흐름의 원칙

이 문서는 현장 작업자가 한 조사 실행을 안전하게 완료하는 표준 흐름을 정의한다. 각 단계에는 다음 네 가지가 있어야 한다.

- 사용자가 선택하거나 수행한 행동
- 시스템이 관찰한 실제 상태
- 그 상태를 확인한 시각과 식별자
- 실패 또는 미확인일 때의 다음 행동

앱의 연결 상태, Jetson 작업 상태, 인터넷 상태, GNSS/RTK 품질, 업로드 상태는 서로 다른 사실이다. 하나의 초록색 표시로 합치지 않는다.

## 2. 실행 전 준비

운영자는 출발 전 다음 정보를 준비한다.

- 배정된 `projectId`와 `sectionId`
- 사용할 Jetson의 `deviceId` 또는 등록 이름
- 사용할 `pipelineId`와 예상 release/config
- 운영 upload target과 직원 인증
- 프로젝트가 정한 필수 센서와 품질 정책

현재 앱 기준선은 프로젝트·구간 entity와 직원 인증을 제공하지 않는다. 통합 구현 전까지 수기 메모로 대체할 수는 있으나, 이는 시연 한계이며 현장 운영 합격으로 인정하지 않는다.

## 3. 정상 흐름

### WF-01 장비 연결

1. 등록된 장비 목록에서 조사 대상 장비를 명시적으로 선택한다.
2. 현장 조건에 따라 같은 Wi-Fi의 LAN 또는 **장비에 직접 연결**인 Wi-Fi Direct로 IP 제어 연결을 만든다.
3. 앱은 인증된 endpoint의 `deviceId`가 선택 장비와 같은지, 전체 제어 기능이 가능한지 확인한다.

정상 완료는 선택 장비 identity, 연결 경로, 마지막 확인 시각, 지원 기능이 보이는 상태다. BLE만 연결되면 기본 상태와 제한 명령은 가능하지만 파일·pipeline·upload 전체 흐름 준비 완료는 아니다.

### WF-02 프로젝트와 조사 구간 선택

1. 배정된 프로젝트를 선택한다.
2. 해당 프로젝트의 조사 구간을 선택한다.
3. 앱은 직원의 프로젝트 접근 권한과 구간의 최신 정보를 확인한다.

정상 완료는 `projectId`, `sectionId`, 표시 이름이 현재 실행 context에 고정된 상태다. 이후 장비 재연결이나 화면 이동으로 이 context가 바뀌면 안 된다. 사용자가 바꾸려면 실행 전 명시적으로 다시 선택한다.

### WF-03 수집 작업 선택

1. 선택 구간에서 실행할 작업을 고른다.
2. 앱은 `pipelineId`, label, source revision, config, output root/path를 보여 준다.
3. 관리자가 아닌 현장 작업자는 새 pipeline 등록이나 임의 YAML 변경 흐름으로 우회하지 않는다.

정상 완료는 한 작업이 현재 실행 후보로 고정되고 Jetson의 실제 등록 상태가 확인된 상태다.

### WF-04 시작 점검

앱은 한 화면에서 항목별 상태와 관찰 시각을 보여 준다.

| 점검 항목 | 필수 관찰값 | 처리 |
|---|---|---|
| 장비 | 선택 `deviceId`, 인증 endpoint, 제어 가능 여부 | 불일치/인증 실패는 시작 차단 |
| 작업 | pipeline 존재, 현재 비실행, release/config | 이미 실행 중이면 새 시작 대신 기존 실행 확인 |
| 시간 | Jetson 시간 동기화 결과 | 동기화 실패 정책은 작업별 blocker로 명시 |
| 저장 | output root/path, 쓰기 가능, 여유 용량 | 작업 정책상 최소치 미달이면 시작 차단 |
| 센서 | 필수/선택 구분, 상태, 관찰 시각 | 승인된 필수 센서 실패만 차단 |
| GNSS/RTK | 관찰 mode/fix/age 등 원자료 | 승인 임계값 전에는 경고·기록, 임의 pass/fail 금지 |
| 인터넷/서버 | 업로드 target, receiver 도달성 | 수집과 실시간 업로드 정책에 따라 별도 표시 |

점검 snapshot은 실행 metadata에 연결해 나중에 같은 실행의 시작 근거를 찾을 수 있어야 한다.

### WF-05 수집 시작

1. 사용자가 장비·프로젝트·구간·작업 요약을 확인하고 한 번 시작한다.
2. 앱은 중복 입력을 막고 Jetson에 start를 전송한다.
3. start 응답 후 pipeline 실제 상태와 새 실행 identity를 조회한다.

정상 완료 조건은 동일 `pipelineId`가 `RUNNING`이고, 새 `runId` 또는 `logId`, `startedAt`, 선택한 project/section context가 연결된 상태다. 요청의 HTTP 성공이나 `STARTING`만으로 수집 시작 완료라고 하지 않는다.

### WF-06 수집 감시

수집 화면은 최소한 다음 정보를 독립적으로 보여 준다.

- 대상 장비와 프로젝트/구간/작업
- 실행 상태와 경과 시간
- 앱↔Jetson 연결 상태와 마지막 관찰 시각
- Jetson 수집 지속 상태
- GNSS/RTK와 필수/선택 센서 상태
- 저장 경로와 기록량 또는 최신 파일 정보
- 문제 구간과 경고

RTK 품질이 낮아져도 기본 행동은 수집 지속과 문제 구간 기록이다. 승인된 작업 정책이 명시적으로 중단을 요구하는 경우에만 차단 또는 중단한다.

### WF-07 연결 복구

1. 앱이 끊기면 Jetson 수집이 중단되었다고 추정하지 않는다.
2. 화면은 마지막으로 확인한 `RUNNING` 상태와 관찰 시각을 과거 사실로 표시하고 현재 상태를 **확인 필요**로 바꾼다.
3. 같은 장비에 재인증한 뒤 pipeline, 실행 이력, 로그, 저장 상태를 다시 조회한다.
4. start/stop 응답이 유실된 경우 실제 상태를 먼저 확인하고 그 결과에 따라 다음 행동을 결정한다.

재연결 후 `RUNNING`이면 기존 `runId/logId`를 이어서 표시한다. `STOPPED`, `FAILED`, 새 실행 identity 또는 장비 identity 불일치이면 즉시 운영자에게 차이를 보여 준다.

### WF-08 수집 종료

1. 사용자가 종료를 선택한다.
2. 앱은 stop을 한 번 전송하고 `STOPPING`/미확인 상태를 표시한다.
3. Jetson에서 비실행 상태, `finishedAt`, 결과/exit code, 로그 마감을 관찰한다.

정상 종료 확인과 수집 성공 판정은 구분한다. `STOPPED`가 정상적인 operator stop인지 `COMPLETED`가 필요한지는 pipeline 정책에 따라 결정하며, 현재 인간 PM 결정이 필요하다. `FAILED`는 종료되었더라도 정상 수집 완료가 아니다.

### WF-09 Jetson 저장 확인

1. 종료된 실행에서 output root/path 또는 결과 session을 연다.
2. 경로 존재, 기대 파일, 파일 수·총량, 기록 종료 시각을 확인한다.
3. 실행 identity와 출력 identity를 연결해 저장 확인 시각을 기록한다.

현재 기준선의 장치 저장소 탐색은 경로와 개별 파일을 보여 주지만 실행→출력 session의 명시적 연결과 기대 합계 계약은 부족하다. 단순히 저장소 화면이 열렸다는 사실은 저장 확인 완료가 아니다.

### WF-10 서버 수신 확인

1. 업로드 source가 WF-09의 출력과 같은지 확인한다.
2. 운영 upload target으로 전송한다.
3. queue 상태가 `QUEUED` → `SCANNING` → `UPLOADING` → `COMPLETED`로 바뀌는 것을 관찰한다.
4. receiver verification에서 `matched=true`, 동일 `remoteSessionId`, 파일 수·총량·content hash를 확인한다.

전송 완료 뒤에도 검증 불일치면 오류다. 검증 전에는 부분 성공이다. 원본 삭제 자격은 수신 완료와 검증 이후의 별도 상태이며 자동 삭제를 뜻하지 않는다.

### WF-11 서버 직접 조회

1. Jetson 연결을 사용하지 않는 조건에서 휴대전화 인터넷으로 운영 receiver에 로그인한다.
2. 프로젝트 권한 범위에서 동일 `remoteSessionId`를 찾는다.
3. session 요약, 파일 목록, verification을 열고 WF-10 증거와 일치하는지 확인한다.
4. 조회 시각을 기록한다.

현재 Android의 서버 데이터 화면은 Jetson API proxy를 사용하므로 이 단계를 충족하지 않는다. receiver 자체에는 bearer 인증 library API가 있지만 이는 장비 token이며 직원 역할/프로젝트 권한을 대체하지 않는다. AG05 결과가 독립 Android client와 직원 권한을 실제로 구현했는지 통합 단계에서 확인한다.

## 4. 오류 흐름

| 단계 | 확정 오류 | 안전한 행동 |
|---|---|---|
| 연결 | 다른 device identity, TLS/HMAC 인증 실패 | 명령 금지, 대상 장비 재선택·진단 |
| 프로젝트/구간 | 없음, 폐쇄됨, 권한 거절 | 실행 시작 금지, 배정 확인 |
| 시작 점검 | 승인된 blocker 실패 | 실패 항목 해결 후 전체 점검 재실행 |
| 시작 | Jetson이 start 실패 또는 pipeline `FAILED` 보고 | 로그·설정·센서 원인 확인, 같은 상태 확인 전 재시작 금지 |
| 수집 | pipeline `FAILED`, 저장 오류 | 현장 안전 확보, 로그/부분 원본 보존, 재수집 판단 |
| 종료 | stop 명시 실패, 제한 시간 뒤에도 실행 유지 | 실제 상태 재조회, 관리자 escalation. 강제 종료는 별도 권한 |
| Jetson 저장 | output 없음, 읽기 실패, 기대 합계 불일치 | 원본 삭제/업로드 완료 처리 금지, 실행 로그와 storage 진단 |
| 업로드 | job `FAILED`, 인증·quota·network 오류 | Jetson 원본 유지, 같은 job의 resume/retry 정책 사용 |
| 검증 | `matched=false`, 파일/해시 불일치 | 서버 수신 완료 처리 금지, 원본 유지, receiver 조사 |
| 직접 조회 | 직원 인증/프로젝트 권한 실패, session 불일치 | proxy 성공으로 대체하지 말고 운영 인증·receiver 확인 |

## 5. 부분 성공과 확인 필요 흐름

| 상황 | 확인된 사실 | 아직 주장할 수 없는 사실 | 다음 행동 |
|---|---|---|---|
| start 뒤 응답 유실 | start 요청을 한 번 전송함 | 실행 시작 성공/실패 | 같은 장비의 pipeline과 run identity 재조회 |
| 앱 연결 단절 | 마지막 관찰 시점까지 수집 중이었음 | 현재도 수집 중인지 여부 | 재연결. 중복 start 금지 |
| stop 뒤 응답 유실 | stop 요청을 한 번 전송함 | 종료 완료 | pipeline·run·로그 재조회 |
| 실행 종료, output 스캔 대기 | Jetson 실행이 종결됨 | 저장 완료 | output session과 합계 확인 |
| Jetson 저장 확인, 서버 불가 | 로컬 원본이 존재함 | 서버 수신 | 원본 유지, upload queue에 재개 가능 상태 보존 |
| 전송 100%, 검증 대기 | 모든 byte 전송 보고 | receiver 완전 수신 | upload complete와 verification 조회 |
| receiver 완료, 직접 조회 실패 | Jetson 경유 receiver 결과가 있음 | 직원 관점의 독립 조회와 권한 정상 | 휴대전화 직접 client 인증/권한 복구 |
| cache로 서버 목록 표시 | 마지막 성공 시점의 목록이 있음 | 최신 서버 상태 | `마지막 갱신` 시각 표시, 온라인 재조회 |

## 6. 재시도와 복구 규칙

1. mutation은 한 번 전송한다. 네트워크 계층에서 자동 반복하지 않는다.
2. 결과가 불명확하면 read로 실제 상태를 조정한 다음 다음 mutation을 결정한다.
3. 같은 실행과 upload job/session identity를 유지할 수 있으면 새 항목을 만들지 않고 재개한다.
4. 복구 중에도 마지막 확정 성공 증거와 오류/미확인 증거를 보존한다.
5. 연결 복구가 실패해도 Jetson 원본과 receiver 완료 데이터는 삭제하지 않는다.
6. 다른 장비가 응답하면 복구가 아니라 identity 오류다.

## 7. 작업 종료 체크리스트

현장 작업자는 철수 전에 다음을 확인한다.

- [ ] 올바른 프로젝트·구간·작업·장비가 실행 기록에 연결되어 있다.
- [ ] 실행의 종결 상태, 종료 시각, 결과와 로그를 확인했다.
- [ ] Jetson output 경로와 파일 집합을 확인했다.
- [ ] 서버 upload job과 receiver verification이 완료되었다.
- [ ] 휴대전화 직접 조회에서 동일 session을 확인했다.
- [ ] RTK/센서 문제 구간과 재조사 필요 여부를 기록했다.
- [ ] 원본 보존 또는 삭제 정책을 따랐다.

서버가 불가한 채 철수해야 하면 작업 자체를 실패로 바꾸지 않는다. **Jetson 저장 확인 완료 / 서버 전송 대기**로 인계하고 장비, 실행, 경로, job ID, 마지막 관찰 시각을 남긴다.
