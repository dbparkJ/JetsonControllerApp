# 2026-09-08 실기기 연결·업로드 디버깅

기준: [검토 및 개선방향](JetsonControllerApp_검토_및_개선방향_2026-09-05.md), [앞선 안정성 개선](RELIABILITY_IMPROVEMENTS_2026-09-08.md).

## 확인한 문제와 수정

- 이전 앱 로그에서 휴대전화 `111.111.111.192`가 Jetson의 유선 주소 `192.168.1.102:8765`로 연결하다 5초 후 시간 초과가 발생했다. NSD의 전체 주소(API 34 이상)를 확인해 휴대전화와 같은 서브넷을 우선하고, 유효한 라우팅 주소도 후보로 유지한다. API 31–33은 기존 단일 주소 API를 사용한다. IPv6 link-local과 Direct 인터페이스는 LAN 후보에서 제외한다.
- SSID가 숨겨지거나 유선·다른 AP를 사용하는 경우에도 발견 주소와 인증 응답으로 LAN 연결을 판단한다. 일반 Wi-Fi 연결 여부는 SSID 읽기 권한과 분리하여, Wi-Fi에 연결된 휴대전화에서 자동 Direct가 실행되지 않도록 한다. 접속 시도 중 새 주소를 발견하면 이전 시도 종료 후 다시 평가한다.
- 연결 문제 해결 안내가 화면 맨 위에서 상태 표시줄과 겹쳤다. 안내를 하단으로 옮기고 시스템 탐색 영역의 안전 여백과 본문 공간을 확보했다.
- 연결 복구 후 업로드 원본 용량 계산과 진행 조회를 재개한다. 마지막 업로드 작업 ID는 장비별로 저장한다.
- 업로드 후 서버 탭에 이전 목록이 남았다. 서버 데이터 화면에 진입할 때 현재 위치를 새로 조회한다. 작은 파일의 전송량이 `0.0 MB`로 보이던 표시도 B/KB/MB/GB 단위로 변경했다.
- 홈의 ‘확인이 필요합니다’를 닫아도 재실행·재연결 중 업로드 목록이 잠깐 비면 정상으로 판단해 닫기 기록을 지우고 있었다. 이 삭제 경로를 제거하고 DataStore에 기록을 누적한다. 같은 장비의 동일 실패는 계속 숨기며, 새로운 업로드 ID·실패 내용·작업 결과 등은 별도 문제로 표시한다.

## 최소 검증

- Galaxy S22 Ultra (`SM-S908N`), Android 16, 무선 ADB `111.111.111.192:37869`에서 데이터 유지 설치. 최종 앱 `1.15.3` (`22`).
- APK SHA-256: `49afd594a355d8c1a290b1f341c5ea079796a278fe1f391cbf834e16fef46334`.
- 연결 주소 선택·LAN 후보·자동 연결·업로드 필터·연결 세션 관련 25개 테스트 통과. 추가 알림 수정 후 DashboardHealthTest 6개 통과. 최종 `assembleDebug`, `lintDebug` 성공(오류 0, 경고 68). 반복 전체 테스트는 수행하지 않았다.
- 실제 로그의 `LAN connected to 111.111.111.67:8765`와 홈의 제어 가능·실시간 지표를 확인했다. 초기 일시적 TCP 연결 시간 초과는 자동 재시도 후 복구됐다.
- 별도 `/data/collections/codex-upload-debug-20260908` 폴더에 합성 파일 2개, 총 105 B를 생성했다. 앱에서 해당 폴더와 용량을 확인하고 Operations upload server로 1회 업로드했다. 완료 100%, 파일 2/2, ‘서버 데이터와 원본이 일치합니다.’를 확인했다. 서버 목록의 해당 폴더·파일과 텍스트 미리보기도 확인했다. 실제 수집 데이터는 업로드·삭제하지 않았다.
- 홈 → 작업 → 설정 조회, 센서 상태 → 카메라 프리뷰 화면 진입을 확인했다. 작업 시작·설정 저장·RTK 변경은 수행하지 않았다.
- 앱의 연결 해제 → 허브의 업로드 기록 → 실패 상세 순서로 오프라인 화면을 확인했다. 하단 복구 안내와 비활성 재시도 버튼이 정상 표시됐고 상단 앱바·상태 표시줄은 겹치지 않았다. Wi-Fi와 ADB는 유지했다.
- 최종 앱에서 기존 실패 업로드 경고의 닫기 버튼을 누른 뒤 앱을 강제 종료·재실행했다. LAN 재연결과 업로드 목록 로드가 끝난 홈에서도 경고가 다시 나타나지 않았다. 최종 실행 프로세스 로그에서 FATAL EXCEPTION/ANR 표식은 발견하지 못했다.

## 기존 실패 기록의 범위

기존 `2026-08-19_10-51-09_raw` 기록은 0 B / 62.7 GB, 파일 0/23459이며 오류는 `Storage I/O failed during upload`였다. 백엔드의 이 문구는 파일 I/O뿐 아니라 DNS·소켓·TLS·timeout을 포함한 여러 OSError에 공통 적용되므로, 저장장치 고장으로 단정할 수 없다.

해당 원본 폴더는 존재했고 현재 권한은 root 실행 서비스에서 읽을 수 있는 상태였다. 표본 파일 7개의 첫 1 B씩만 읽어 성공했다. NVMe 여유 공간 약 523 GB, inode 여유 약 98%를 확인했다. 당시 구체적인 예외·실패 단계는 앱 이력에 보존되지 않아 이 문구만으로 복원할 수 없다. root 전용 상태 경로에 대한 추가 접근도 제한됐다. 기존 62.7 GB 작업을 재전송하지 않았으므로 대용량 실패 원인이 해결됐다고 보증하지 않는다.

실행 중인 `/opt/jetson-control` 서비스는 앞선 저장소 변경보다 오래된 버전이다. 이번에는 Android 앱만 설치했으며, 백엔드 배포·재시작과 장시간 대용량 전송·Direct 반복 시험은 수행하지 않았다. 검증용 105 B 폴더와 서버 사본은 확인용으로 남겼다.
